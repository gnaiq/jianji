## 一、设计原则

| # | 原则 | 落地体现 |
|---|---|---|
| DP-1 | **金额一律整数分存储** | `amount_cents INTEGER`，杜绝浮点累积误差 |
| DP-2 | **可派生数据不落库** | 账户余额、预算占用率均实时计算，`accounts.balance` 已被删除 |
| DP-3 | **删除即软删** | `deleted_at` 时间戳，支持回收站与跨会话恢复 |
| DP-4 | **时间统一 ISO-8601 文本** | `Converters` 用 `DateTimeFormatter.ISO_LOCAL_DATE_TIME`，字符串排序 = 时间排序 |
| DP-5 | **枚举存名称字符串** | `TransactionType.name` 等，可读性优先于存储效率 |
| DP-6 | **索引与 Entity 声明必须成对出现在 Migration 中** | Room 会校验全部索引，缺失即启动崩溃 |
| DP-7 | **每次 schema 变更必须有 Migration + schema JSON 基线** | `exportSchema=true`，`room.schemaLocation="$projectDir/schemas"` |

### DP-4 的隐含设计价值

`LocalDateTime` 以 `ISO_LOCAL_DATE_TIME` 文本存储，使 SQLite 的字符串比较天然等价于时间比较。这让 `date >= :start AND date < :end`、`ORDER BY date DESC`、`deleted_at IS NOT NULL` 全部可以直接走 B-Tree 索引，无需函数转换——**这是全部日期范围查询能被索引命中的前提**。

⚠️ 代价：不存时区。跨时区使用（用户出国）会导致日期归属偏移。当前作为单机个人记账可接受，若未来做云同步必须重新设计（见 §八 V-3）。

## 二、ER 模型

```
                    ┌──────────────┐
                    │  categories  │
                    │  (自引用树)   │
                    │ parentId → id│
                    └──────┬───────┘
                           │ 1
                           │ FK CASCADE
                           │ N
┌──────────┐        ┌──────▼────────┐        ┌──────────────────┐
│ accounts │ 0..1   │ transactions  │  N   N │  transaction_tags│  N   1 ┌──────┐
│          ├───────►│               │◄───────┤   (联结表)        ├───────►│ tags │
│          │ accountId              │        │ PK(txId, tagId)  │        └──────┘
│          │ 0..1   │               │        └──────────────────┘
│          ├───────►│  toAccountId  │              CASCADE 双向
└──────────┘        └───────────────┘

┌──────────┐   ┌────────────────────────┐   ┌──────────────────┐
│ budgets  │   │ recurring_transactions │   │ quick_templates  │
│ (无 FK)   │   │       (无 FK)           │   │     (无 FK)       │
│ categoryId│   │ categoryId, accountId  │   │ categoryId,      │
│ 逻辑引用   │   │      逻辑引用            │   │ accountId 逻辑引用 │
└──────────┘   └────────────────────────┘   └──────────────────┘
```

### 外键约束现状盘点（重要缺陷）

| 关系 | 是否有 DB 级外键 | 说明 |
|---|---|---|
| `transactions.categoryId → categories.id` | ✅ `ON DELETE CASCADE` | — |
| `transaction_tags.transactionId → transactions.id` | ✅ `ON DELETE CASCADE` | — |
| `transaction_tags.tagId → tags.id` | ✅ `ON DELETE CASCADE` | — |
| `transactions.accountId → accounts.id` | ❌ **无外键** | 靠 `TransactionDao.clearAccount()` 应用层置 NULL |
| `transactions.toAccountId → accounts.id` | ❌ **无外键** | 靠 `clearToAccount()` |
| `budgets.categoryId → categories.id` | ❌ **无外键** | 删分类后预算成孤儿 |
| `recurring_transactions.categoryId / accountId` | ❌ **无外键** | 删分类后周期任务执行即崩或写入悬空 ID |
| `quick_templates.categoryId / accountId` | ❌ **无外键** | 同上 |

> **结论：4 张表 6 处引用完全靠应用层自律。** 其中 `transactions.accountId` 尚有 `clearAccount()` 兜底，而 `budgets` / `recurring_transactions` / `quick_templates` 的 `categoryId` **连应用层清理都没有**——删除分类会直接产生悬空引用。这是当前数据模型最大的完整性缺口（见 §七 C-2）。

## 三、表结构详细设计

### 3.1 `transactions`（交易流水 · 核心表）

| 列 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | INTEGER | PK AUTOINCREMENT | — |
| `categoryId` | INTEGER | NOT NULL, **FK → categories.id CASCADE** | 转账时指向系统分类「转账」 |
| `amount_cents` | INTEGER | NOT NULL | **分**。展示 `/100.0`，输入 `Math.round(yuan*100)` |
| `type` | TEXT | NOT NULL | `INCOME` / `EXPENSE` / `TRANSFER` |
| `description` | TEXT | NOT NULL DEFAULT '' | 备注，搜索字段 |
| `date` | TEXT | NOT NULL | ISO-8601，业务发生时间 |
| `accountId` | INTEGER | NULL | 转账时为**转出**账户 |
| `toAccountId` | INTEGER | NULL | 仅 `type=TRANSFER` 有效，**转入**账户 |
| `deleted_at` | TEXT | NULL | **软删标记**。NULL=未删 |
| `createdAt` | TEXT | NOT NULL | 记录创建时间 |
| `updatedAt` | TEXT | NOT NULL | 最后修改时间 |

**索引**：`accountId`、`description`、`date`、`deleted_at`、`categoryId`（外键自动）

> 设计注记：`date`（业务时间）与 `createdAt`（记录时间）分离，支持"今天补记昨天的账"。所有报表按 `date` 聚合，不用 `createdAt`。

### 3.2 `categories`（分类 · 自引用两级树）

| 列 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | INTEGER | PK AUTOINCREMENT | — |
| `name` | TEXT | NOT NULL | — |
| `icon` | TEXT | NOT NULL DEFAULT '💰' | Emoji |
| `color` | TEXT | NOT NULL DEFAULT '#6200EE' | Hex |
| `type` | TEXT | NOT NULL | `INCOME` / `EXPENSE` |
| `isDefault` | INTEGER | NOT NULL DEFAULT 0 | 预置分类 |
| `isSystem` | INTEGER | NOT NULL DEFAULT 0 | **系统分类**（如「转账」），不在用户列表展示 |
| `sortOrder` | INTEGER | NOT NULL DEFAULT 0 | — |
| `parentId` | INTEGER | NOT NULL DEFAULT 0 | **0 = 一级分类**；非 0 = 父分类 id |

**树结构设计辨析**：用 `parentId=0` 表示根，而非 `NULL`。好处是列可 NOT NULL、查询无需 `IS NULL` 分支（`Category.isMajor get() = parentId == 0L`）；坏处是无法建真正的自引用外键（0 不是合法 id）。当前**仅支持两级**，无深度约束保护——应用层若允许把二级分类设为父级会产生三级甚至环，需在 UseCase 层校验。

⚠️ **`color` NOT NULL 的历史血案**：`MIGRATION_3_4` 插入系统「转账」分类时若不显式赋 `color`，会触发 `NOT NULL constraint failed`，导致 v3→v4 升级用户**启动即闪退**（v1.6.0 回归根因）。迁移中已补 `UPDATE categories SET color='#6200EE' WHERE color IS NULL` 兜底。
> 教训沉淀：**任何 Migration 中的 INSERT 必须显式列出所有 NOT NULL 且无默认值的列。**

### 3.3 `accounts`（账户）

| 列 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | INTEGER | PK AUTOINCREMENT | — |
| `name` | TEXT | NOT NULL | — |
| `icon` | TEXT | NOT NULL DEFAULT '💳' | — |
| `isDefault` | INTEGER | NOT NULL DEFAULT 0 | 默认账户，**业务上应全局唯一** |

**`balance` 列已在 `MIGRATION_6_7` 中移除**（ADR-2）。

**唯一默认账户的保证**：DB 层**无**唯一约束，靠 `AccountDao.setDefaultAtomic(id)` 在同一事务内先 `clearDefaults()` 再 `setDefault(id)`。这是正确做法，但**约束不在 DB 层**——任何绕过该方法的写入（如导入恢复）都可能产生多个默认账户。

### 3.4 `budgets`（预算）

| 列 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | INTEGER | PK AUTOINCREMENT | — |
| `categoryId` | INTEGER | NULL，**FK → categories.id ON DELETE NO ACTION** | **NULL = 总预算**；非空 = 分类预算 |
| `amount_cents` | INTEGER | NOT NULL | ✅ **v1.6.30 (MIGRATION_8_9) 已迁为 Long 分**，展示 `/100.0`，输入 `Math.round(yuan*100)` |
| `period` | TEXT | NOT NULL | `MONTHLY` / `YEARLY` |
| `year` | INTEGER | NOT NULL | — |
| `month` | INTEGER | NOT NULL DEFAULT 0 | `YEARLY` 时忽略（置 0） |

**唯一索引**：`index_budgets_categoryId_year_month_period`（`categoryId, year, month, period` UNIQUE），由 `MIGRATION_8_9` 在去重后建立，与 `@Entity(indices=[...unique=true])` 一致。

> **v1.6.30 已修复原 §3.4 三项缺陷**：
> - 缺陷 1（数据类型）：`amount REAL → amount_cents INTEGER`，预算进度全程整数分，占用率精确无抖动。
> - 缺陷 2（唯一性）：`MIGRATION_8_9` 先按 `(categoryId, year, month, period)` 去重（保留 MAX(id)）再建唯一索引，`upsertBudget` 幂等由 DB 唯一约束兜底。
> - 缺陷 3（无外键）：`categoryId` 加 `FK → categories.id ON DELETE NO ACTION`；删分类时由应用层 `reassign` 后再删（见 `CategoryRepository.deleteCategory`），孤儿预算不再悬空。

### 3.5 `tags` / `transaction_tags`（标签系统）

**`tags`**：`id` / `name` / `color`(默认 `#6200EE`) / `icon`(默认 `🏷️`) / `sortOrder`

**`transaction_tags`**：复合主键 `(transactionId, tagId)`，双向 `CASCADE`，`tagId` 单列索引

> 设计得当的一张表：复合主键天然防重复关联；`tagId` 单独索引支持"按标签反查交易"（`transactionId` 已是主键前缀，无需额外索引）。

**与软删除的交互隐患**：交易被软删（`deleted_at` 非空）时，`transaction_tags` 行**依然存在**（CASCADE 只在硬删触发）。`getTransactionsByTagIds()` 必须自行带 `deleted_at IS NULL`，否则回收站里的交易会出现在标签筛选结果中。

### 3.6 `recurring_transactions`（周期记账模板）

| 列 | 类型 | 说明 |
|---|---|---|
| `id` / `categoryId` / `amount_cents` / `type` / `description` / `accountId` | — | 交易模板字段 |
| `frequency` | TEXT | `DAILY` / `WEEKLY` / `MONTHLY` / `YEARLY` |
| `interval` | INTEGER DEFAULT 1 | 每 N 个 frequency 执行一次 |
| `dayOfMonth` | INTEGER DEFAULT 1 | MONTHLY/YEARLY：几号 |
| `monthOfYear` | INTEGER DEFAULT 1 | YEARLY：几月（`MIGRATION_3_4` 新增，**修复此前写死 1 月的 bug**） |
| `dayOfWeek` | INTEGER DEFAULT 1 | WEEKLY：周一=1…周日=7 |
| `nextRunDate` | TEXT NOT NULL | **调度游标** |
| `isActive` | INTEGER DEFAULT 1 | — |
| `createdAt` | TEXT NOT NULL | — |

**关键查询**：`getDue(now)` = `WHERE nextRunDate <= :now AND isActive = 1`

⚠️ **缺索引**：该查询在 `nextRunDate` 上无索引。当前模板数量少（个位数）可接受，但这是**每次启动都执行**的查询，模板增多后应补 `Index(["nextRunDate", "isActive"])`。

⚠️ **无幂等键**：表中没有"上次成功生成到哪一天"的记录，catch-up 的正确性完全依赖 `nextRunDate` 的原子推进。若生成交易成功但更新 `nextRunDate` 失败（未包事务），会**重复记账**。

### 3.7 `quick_templates`（快捷记账模板）

`id` / `categoryId` / `amount_cents` / `type` / `description` / `accountId` / `sortOrder` / `useCount`

`useCount` 用于按使用频率排序（`ORDER BY sortOrder ASC, useCount DESC`）。无外键、无索引，数据量小可接受。

## 四、索引设计

### 4.1 现有索引

| 表 | 索引名 | 列 | 服务的查询 | 评估 |
|---|---|---|---|---|
| transactions | `index_transactions_date` | `date` | 日期范围过滤 + SUM 聚合（首页/历史/统计） | ✅ 必需 |
| transactions | `index_transactions_accountId` | `accountId` | `getByAccount()`、余额聚合 | ✅ 必需 |
| transactions | `index_transactions_deleted_at` | `deleted_at` | 回收站 / 软删过滤 | 🟡 见 4.2 |
| transactions | `index_transactions_description` | `description` | 备注搜索 | 🟠 见 4.2 |
| transactions | `index_transactions_categoryId` | `categoryId` | 外键自动索引 | ✅ 必需 |
| transaction_tags | `index_transaction_tags_tagId` | `tagId` | 按标签反查 | ✅ 必需 |

### 4.2 索引问题诊断

**问题 1：`description` 索引基本无效。** 备注搜索必然是 `LIKE '%keyword%'`（前缀通配），SQLite 的 B-Tree 索引**无法用于前导通配的 LIKE**。这个索引占用写入开销却几乎不产生查询收益。
> 建议：要么删除，要么改用 FTS4/FTS5 虚拟表做全文检索。

**问题 2：`deleted_at` 单列索引选择性极低。** 绝大多数行 `deleted_at IS NULL`，索引选择性接近 0。它只对"查回收站"（`IS NOT NULL`，命中极少行）有效，对占 99% 查询的 `IS NULL` 过滤无用。
> 保留即可（回收站场景确实受益），但不要指望它加速主列表。

**问题 3：缺少高价值复合索引。** 最高频的查询形态是：
```sql
WHERE deleted_at IS NULL AND date >= ? AND date < ?  ORDER BY date DESC
```
当前只能用 `index_transactions_date` 单列索引，`deleted_at` 过滤需回表逐行判断。
> 建议新增：`Index(value = ["deleted_at", "date"])`。SQLite 可用该复合索引同时完成过滤与排序（`deleted_at` 等值 + `date` 范围/排序，符合最左前缀）。

**问题 4：`recurring_transactions.nextRunDate` 无索引**（见 3.6）。

### 4.3 索引变更铁律

Entity 的 `indices` 声明与 Migration 的 `CREATE INDEX` **必须成对出现**。

> 血案佐证：实体自 v1 起就声明了 `accountId`/`description` 索引，但迁移链 1→2→3→4 **从未 CREATE INDEX**。Room 在迁移后会校验全部索引，老升级用户因缺索引而**启动崩溃**。`MIGRATION_4_5` 才用 `CREATE INDEX IF NOT EXISTS` 防御性补齐。
>
> 同类问题在 `MIGRATION_5_6` 重建表时再次出现——外键自动索引 `index_transactions_categoryId` 也从未被历史迁移创建过，重建时一并补上。
>
> **索引名必须与 Room 生成的名称逐字一致**（`index_<表名>_<列名>`），否则 schema 校验失败。

## 五、迁移链设计

### 5.1 迁移全景（v1 → v7）

| 迁移 | 版本对应 | 变更内容 | 风险点 |
|---|---|---|---|
| `MIGRATION_1_2` | 早期 | 建 `accounts`(含 balance) / `budgets` / `recurring_transactions` / `quick_templates`；`transactions` 加 `accountId`；`categories` 加 `sortOrder` | ADD COLUMN，低风险 |
| `MIGRATION_2_3` | — | `categories` 加 `parentId INTEGER NOT NULL DEFAULT 0`（子分类） | 低 |
| `MIGRATION_3_4` | v1.6.0 | `transactions` 加 `toAccountId`；`recurring` 加 `monthOfYear`；`categories` 加 `isSystem`；**INSERT 系统「转账」分类** | 🔴 `color` NOT NULL 未赋值曾致**启动闪退** |
| `MIGRATION_4_5` | — | 建 `index_transactions_date`；**防御性补齐** `accountId`/`description` 索引 | 🔴 修复历史索引缺失导致的崩溃 |
| `MIGRATION_5_6` | v1.6.6 | **重建 `transactions` 表**：`amount REAL → amount_cents INTEGER`（`ROUND(amount*100)`）、新增 `deleted_at`、重建全部 5 个索引；建 `tags` + `transaction_tags` | 🔴 全表重建，数据量大时耗时；一旦中断数据丢失 |
| `MIGRATION_6_7` | — | `recurring_transactions` / `quick_templates` 同样迁 `amount → amount_cents`；**`accounts` 移除 `balance` 列**（重建表） | 🔴 三张表重建 |
| `MIGRATION_7_8` | v1.6.27 | 重建 `transactions` 表：`categoryId` 外键 `ON DELETE` 由 CASCADE 改为 **NO ACTION**（修复删分类级联误删转账/回收站） | 🔴 全表重建 |
| `MIGRATION_8_9` | v1.6.30 | 重建 `budgets` 表：`amount REAL → amount_cents INTEGER`（ROUND 舍入）；**先按 (categoryId,year,month,period) 去重保留 MAX(id) 再建唯一索引**；加 `categoryId` 外键 `ON DELETE NO ACTION` | 🔴 全表重建 + schema 变更，须真机升级回归 |

### 5.2 「建新表→迁数据→删旧表→改名」模式

`MIGRATION_5_6` / `6_7` 采用此模式而非 `ALTER TABLE`，原因有三：

1. SQLite 的 `ALTER TABLE` 不支持删列（`accounts.balance`）、不支持改列类型（`REAL → INTEGER`）
2. `ALTER ADD COLUMN` 在 NOT NULL/默认值上的行为与 Room 生成的 schema 存在**校验差异**，会导致升级后 schema 不匹配而闪退
3. 重建时可以**顺带补齐历史缺失的索引**（含外键自动索引）

**该模式的固定步骤（必须严格遵守）**：
```sql
1. CREATE TABLE xxx_new (...)     -- 列定义必须与 Room 生成的目标 schema 逐字一致
2. INSERT INTO xxx_new SELECT ... FROM xxx   -- 显式列出所有列，不用 SELECT *
3. DROP TABLE xxx
4. ALTER TABLE xxx_new RENAME TO xxx
5. CREATE INDEX IF NOT EXISTS ...  -- 重建全部索引，含外键自动索引
```

### 5.3 `fallbackToDestructiveMigration` 的定位

**已开启。用途仅限：版本回退（降级）时避免 Room 拒绝降级导致闪退**，代价是回退会清空 DB（已在 rollback 脚本中说明，属回退预期内的数据损失）。

> ⚠️ **严禁**将其作为"忘写升级 Migration"的兜底。它的存在使得漏写 Migration **不会在开发期报错，而是静默清空用户数据**。这正是 §六 R2（迁移测试）必须优先落地的根本原因。

### 5.4 迁移测试基线（当前缺失，最高优先级）

配置已就位：
```kotlin
// app/build.gradle.kts
ksp { arg("room.schemaLocation", "$projectDir/schemas") }
sourceSets.getByName("androidTest").assets.srcDir("$projectDir/schemas")
// 依赖
androidTestImplementation("androidx.room:room-testing:2.6.1")
```

**缺的是**：`app/schemas/*.json` 未提交入库，且**零个** Migration 测试。

**补齐方案**：

```kotlin
@RunWith(AndroidJUnit4::class)
class Migration6To7Test {
    @get:Rule
    val helper = MigrationTestHelper(
        InstrumentationRegistry.getInstrumentation(),
        JianjiDatabase::class.java
    )

    @Test
    fun migrate6To7_convertsAmountToCents_andDropsBalance() {
        helper.createDatabase(TEST_DB, 6).apply {
            execSQL("INSERT INTO quick_templates (categoryId, amount, type, description, sortOrder, useCount) VALUES (1, 12.34, 'EXPENSE', 'x', 0, 0)")
            execSQL("INSERT INTO accounts (name, icon, balance, isDefault) VALUES ('现金','💳',999.0,1)")
            close()
        }
        val db = helper.runMigrationsAndValidate(TEST_DB, 7, true, JianjiDatabase.MIGRATION_6_7)
        // 断言 1：金额精确转换（12.34 → 1234），不丢精度
        db.query("SELECT amount_cents FROM quick_templates").use {
            it.moveToFirst(); assertEquals(1234L, it.getLong(0))
        }
        // 断言 2：balance 列已移除且账户数据保留
        db.query("SELECT name, isDefault FROM accounts").use {
            it.moveToFirst(); assertEquals("现金", it.getString(0))
        }
    }
}
```

**每条迁移的测试必须断言三件事**：① 表结构正确（`runMigrationsAndValidate` 自动校验）；② **数据不丢且值正确**；③ 索引存在（`PRAGMA index_list`）。

## 六、查询设计

### 6.1 聚合下推原则

```sql
-- ✅ 现有实现：SUM 在 SQLite 内完成
SELECT SUM(amount_cents)/100.0 FROM transactions
WHERE deleted_at IS NULL AND type = :type AND date >= :startDate AND date < :endDate
```

避免把万行数据读进内存再 Kotlin 侧 `fold`。这一点现有 DAO 做得正确。

⚠️ 但 `SUM(amount_cents)/100.0` 返回 `Double?`，在 DB 层就把整数分转成了浮点——**违背 DP-1 的初衷**。
> 建议：改为 `SUM(amount_cents)` 返回 `Long?`，除 100 的动作留到展示层。这样中间聚合结果全程整数，彻底无浮点误差。

### 6.2 日期区间半开原则

全部区间查询统一 `date >= :start AND date < :end`（左闭右开），避免 `BETWEEN` 在毫秒边界上重复统计跨月最后一笔。现有 DAO 已一致遵守。

### 6.3 Flow vs suspend 的选型

| 后缀/形式 | 语义 | 用于 |
|---|---|---|
| `observeXxx()` / 返回 `Flow` | 持续订阅，DB 变更自动推送 | UI 列表、汇总卡片 |
| `getXxx()` `suspend` | 一次性读取 | 编辑前取详情、业务校验 |
| `getXxxSnapshot()` `suspend` | 一次性读 List | 导出、统计计算、备份 |

命名已基本一致，是本项目 DAO 层做得好的地方。

### 6.4 软删除过滤（最易漏的地方）

`TransactionDao` 中除三个明确的例外，**所有查询都必须带 `deleted_at IS NULL`**：

| 例外方法 | 为何不带 | 
|---|---|
| `getById(id)` | 回收站恢复需要读到已删记录 |
| `getDeletedTransactions()` | 就是查回收站 |
| `getAllIncludingDeletedSnapshot()` | 备份需含已删记录（恢复后回收站内容不丢） |

> **治理建议**：新增任何 `transactions` 查询时，Review 必须回答一句「这条查询该不该过滤软删」。这是纯人工纪律，无编译期保护——建议在 DAO 文件头部写死这条注释，并在 PR 模板中列为勾选项。

## 七、数据完整性与一致性

| ID | 一致性要求 | 当前保障 | 缺口 |
|---|---|---|---|
| C-1 | 一笔交易的标签必须与交易同生共死 | `transaction_tags` 双向 CASCADE + 写入包 `withTransaction` | 🟡 软删时关联行仍在，查询需自行过滤 |
| **C-2** | 分类被删时，引用它的预算/周期/模板不能悬空 | `transactions` 有 CASCADE | 🔴 `budgets` / `recurring_transactions` / `quick_templates` **既无外键也无应用层清理** |
| C-3 | 账户被删时，交易的 `accountId` 应置 NULL | `clearAccount()` / `clearToAccount()` 应用层处理 | 🟡 无外键 `SET NULL`，依赖调用方记得调 |
| C-4 | 默认账户全局唯一 | `setDefaultAtomic()` 事务内 clear+set | 🟡 DB 无唯一约束，导入路径可绕过 |
| C-5 | 同一 `(categoryId, year, month, period)` 只能有一条预算 | `upsertBudget()` 先查后插 | 🔴 **无唯一索引**，重复行会导致 `LIMIT 1` 静默取错 |
| C-6 | 转账双边金额相等 | 单条记录天然保证 | ✅ 结构性保证 |
| C-7 | 账户余额 = 流水之和 | 动态计算 | ✅ 结构性保证（ADR-2 的核心收益） |
| C-8 | 周期任务不重复记账 | `nextRunDate` 原子推进 | 🔴 无幂等键；生成与推进若未同事务则可能重复 |

### 优先整改（按危害排序）

1. **C-2**：给 `budgets.categoryId` / `recurring_transactions.categoryId` / `quick_templates.categoryId` 增加外键（`ON DELETE CASCADE` 或 `SET NULL`），或在 `CategoryRepository.delete()` 中统一清理。**推荐加真外键**——应用层清理靠自律，外键靠引擎。
2. **C-5**：给 `budgets` 加唯一索引 `(categoryId, year, month, period)`，配合 `OnConflictStrategy.REPLACE` 实现真 upsert。
3. **C-8**：周期记账「生成交易 + 推进 nextRunDate」必须在同一 `withTransaction` 内。

## 八、规划中的 Schema 演进

### V-1：v7 → v8（预算金额迁移 + 完整性补齐）★ 建议下个迭代

```sql
-- 1. budgets.amount REAL → amount_cents INTEGER（重建表模式）
CREATE TABLE budgets_new (
    id INTEGER PRIMARY KEY AUTOINCREMENT NOT NULL,
    categoryId INTEGER,
    amount_cents INTEGER NOT NULL,
    period TEXT NOT NULL,
    year INTEGER NOT NULL,
    month INTEGER NOT NULL DEFAULT 0,
    FOREIGN KEY(categoryId) REFERENCES categories(id) ON DELETE CASCADE  -- 顺带补 C-2
);
INSERT INTO budgets_new (id, categoryId, amount_cents, period, year, month)
    SELECT id, categoryId, CAST(ROUND(amount * 100) AS INTEGER), period, year, month FROM budgets;
DROP TABLE budgets;
ALTER TABLE budgets_new RENAME TO budgets;

-- 2. 唯一索引（修 C-5）—— ⚠️ 建唯一索引前必须先去重，否则迁移失败
DELETE FROM budgets WHERE id NOT IN (
    SELECT MAX(id) FROM budgets GROUP BY COALESCE(categoryId,-1), year, month, period
);
CREATE UNIQUE INDEX IF NOT EXISTS index_budgets_unique
    ON budgets (categoryId, year, month, period);

-- 3. 外键自动索引
CREATE INDEX IF NOT EXISTS index_budgets_categoryId ON budgets (categoryId);
```

> ⚠️ 去重步骤不可省略。若存量数据已有重复预算行，直接建唯一索引会让整条迁移抛异常，**升级用户启动即崩**。

### V-2：v8 → v9（查询性能）

```sql
CREATE INDEX IF NOT EXISTS index_transactions_deleted_at_date
    ON transactions (deleted_at, date);                     -- 修 §4.2 问题 3
CREATE INDEX IF NOT EXISTS index_recurring_nextRunDate_isActive
    ON recurring_transactions (nextRunDate, isActive);      -- 修 §3.6
DROP INDEX IF EXISTS index_transactions_description;        -- 修 §4.2 问题 1（LIKE %x% 用不上）
```
> 若备注搜索是高频功能，则不要 DROP，改为引入 FTS5 虚拟表 `transactions_fts`，另立迁移。

### V-3：远期（不在当前路线图）

| 项 | 触发条件 | 说明 |
|---|---|---|

## 九、数据库治理规范

### 9.1 变更 Checklist（改任何 Entity 前逐条勾）

- [ ] `@Database(version = N+1)`
- [ ] 编写 `MIGRATION_N_N+1` 并在 `addMigrations(...)` **注册**（漏注册 = 静默清库，因 `fallbackToDestructiveMigration` 开着）
- [ ] Migration 中的 `INSERT` **显式列出所有 NOT NULL 无默认值的列**（`MIGRATION_3_4` 血案）
- [ ] Entity 新增/变更 `indices` → Migration 中配套 `CREATE INDEX IF NOT EXISTS`，**索引名与 Room 生成名逐字一致**
- [ ] 建唯一索引前先写去重 SQL
- [ ] 涉及删列/改类型 → 用「建新表→迁数据→删旧表→改名」四步，且**重建全部索引含外键自动索引**
- [ ] 新增/修改列名 → snake_case + 显式 `@ColumnInfo(name=...)`
- [ ] 新增查询 → 明确回答「该不该过滤 `deleted_at IS NULL`」
- [ ] 多表写 → 包 `withTransaction`
- [ ] Repository **显式包装** DAO 新方法（历史踩坑：缺 `BudgetRepository.insert` / `TagRepository.deleteAll` 致 `Unresolved reference`）
- [ ] 影响备份 DTO → 同步更新导入导出 + **release 变体真机回归**（ProGuard/Gson 强耦合）
- [ ] `app/schemas/N+1.json` 生成并**提交入库**
- [ ] 新增 `MigrationNToN+1Test`，断言结构 + 数据 + 索引
- [ ] CI 绿灯（**禁止本地构建，编译验证以 CI 为准**）

### 9.2 命名规范

| 对象 | 规则 | 现状 |
|---|---|---|
| 表名 | 小写复数下划线 | ✅ `transactions` / `quick_templates` / `transaction_tags` |
| 列名 | **新增一律 snake_case**；存量冻结不改名 | 🟡 现存混用（`amount_cents` vs `categoryId`），重命名代价 > 收益 |
| 索引名 | `index_<表>_<列>[_<列>]`（Room 生成规则） | ✅ 一致 |
| Migration 常量 | `MIGRATION_<from>_<to>` | ✅ 一致 |
| 迁移测试 | `Migration<N>To<N+1>Test` | ❌ 尚不存在 |

### 9.3 禁止清单

- ❌ 用 `fallbackToDestructiveMigration` 替代升级 Migration
- ❌ 在 Migration 里 `SELECT *`（列顺序变化会静默错位）
- ❌ 在 DAO 里写业务判断（如 `if 超预算`）
- ❌ 直接暴露 DAO 给 ViewModel（必须经 Repository）
- ❌ 金额用 `Double`/`Float` 参与计算或存储（`budgets.amount` 是待清理的历史遗留）
- ❌ 新增查询忘记 `deleted_at IS NULL`
- ❌ 本地构建后宣称"编译通过"
