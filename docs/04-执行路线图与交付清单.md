## 一、项目基线与约束

### 1.1 团队与节奏

| 项 | 设定 |
|---|---|
| 团队规模 | 1 人（单人维护） |
| 迭代长度 | **2 周 / Sprint** |
| 容量假设 | 每 Sprint 有效开发 **8 人日**（业余项目按 40% 投入计） |
| 发版节奏 | 每 Sprint 结束发一个 patch/minor 版本 |
| 版本策略 | `versionCode` 每发版 +1；`versionName` 与 annotated tag 严格一致 |

### 1.2 硬性约束（不可协商）

| # | 约束 | 对计划的影响 |
|---|---|---|
| CT-1 | **APK 必须由 GitHub Actions CI 构建，禁止本地构建**；编译验证以 CI 为准 | 每个任务的 DoD 必须包含 CI 绿灯；本地 lint=0 不作数 |
| CT-2 | 无服务端、无远程数据兜底 | 数据类缺陷一律 P0；灰度回滚只能靠用户重装 + 备份 |
| CT-3 | release 与 debug 行为不同（R8 混淆） | 涉及 DTO/序列化/包结构的改动，**必须 release 变体真机验收** |
| CT-4 | `fallbackToDestructiveMigration` 已开启 | 漏写 Migration = 静默清库且开发期不报错 → 迁移测试是**前置刚需** |
| CT-5 | 重发同版本必须先 `DELETE /releases/{id}` | 发布 checklist 固定项 |

### 1.3 排期第一原则

> **不可逆 > 可逆。** 优先修复「一次操作即导致用户数据永久丢失」的缺陷，其次修复「可通过重新操作纠正」的问题，最后做重构与优化。

### 2.2 逆向推导：从目标倒推里程碑

```
终态目标：一个「数据不会丢、账目不会错、结构可持续演进」的个人记账 App
   │
   ├─ 目标 A：用户数据在任何操作下都不会永久丢失
   │     ← 前置：误删保护（B1-4/B5-6/B7-5）+ 备份可用且安全（P6-1/P6-2/P6-3）
   │
   ├─ 目标 B：所有数字都是对的
   │     ← 前置：金额全链路整数（B3-4/D4-1）+ 预算唯一性（D4-2）+ 周期不重复（D2-1/D2-2）
   │     ← 前置的前置：★ 迁移测试与 schema 基线（R2）—— 否则不敢动数据
   │
   └─ 目标 C：结构可持续演进
         ← 前置：domain 层（S1/R7）+ utils 拆解（S2）+ 巨型文件（S3/R8）+ DI 收敛（S4/R9）
         ← 前置的前置：测试骨架（S5）—— 否则重构没有安全网
```

**推导出的两个"前置的前置"**：`R2 迁移测试` 与 `S5 测试骨架`。它们本身不产生任何用户价值，但**没有它们，目标 B 与目标 C 的所有任务都不敢动手**。因此必须放在 Sprint 1。

### 2.3 里程碑定义

| 里程碑 | 名称 | 目标 | 版本 | 完成判据 |

### 排期理由说明

| 决策 | 理由 |
|---|---|
| M0 排最前，且不出任何用户可见功能 | CT-4 决定了没有迁移测试就不敢改 schema；Sprint 3 的 DB v8 强依赖它 |
| M1（误删保护）在 M2（金额）之前 | 不可逆 > 可逆。误删保护全是应用层校验，**不动 schema，风险最低、收益最高** |
| M2 拆成两个 Sprint | Sprint 3 全是 DB 迁移（高风险，需完整回归窗口）；Sprint 4 是应用层逻辑，风险不同，不宜混排 |
| M3 序列化收敛在加密之前 | 加密改的是备份文件格式；若与 Gson→kotlinx 迁移同期做，一旦出问题**无法定位是加密还是序列化的锅** |
| M4 排最后 | 纯内部重构，零用户价值。放最后是因为它需要前面 Sprint 积累的测试作为安全网 |
