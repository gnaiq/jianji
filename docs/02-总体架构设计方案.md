## 一、架构总览

### 1.1 系统定位

| 维度 | 结论 |
|---|---|
| 形态 | **纯本地（offline-first）单机 Android 应用**，无服务端、无账号体系 |
| 唯一外部依赖 | GitHub Releases API（`UpdateManager` 检查版本更新） |
| 数据主权 | 全量数据仅存在于设备 SQLite + 用户导出的备份文件 |
| 分发 | GitHub Actions CI 构建签名 APK → GitHub Release |
| 规模 | 75 个 Kotlin 文件 / 10112 行 / 8 张表 / 9 条路由 / 6 个 ViewModel |

**架构第一性约束：没有服务端，就没有服务端兜底。** 数据一旦在设备上损坏或迁移失败，用户无处找回。这决定了本架构的三条硬性优先级：

> **数据完整性 > 升级安全性 > 功能丰富度 > 性能 > 代码优雅**

### 1.3 架构风格选择

| 候选 | 是否采用 | 理由 |
|---|---|---|
| **MVVM + 单向数据流（UDF）** | ✅ 采用 | Compose + StateFlow 的天然形态；现有代码已是此形态 |
| Clean Architecture（严格三层 + 依赖倒置） | ⚠️ **部分采用** | 引入 `domain/` 与 Repository 接口，但**不引入** Entity/DomainModel/DTO 三套模型映射——10112 行项目承受不起 3× 模型样板 |
| MVI（严格 Intent/Reducer） | ❌ 不采用 | 收益主要在复杂状态机；本项目状态复杂度不足以覆盖 Reducer 样板成本 |
| 多模块 | ❌ 不采用 | 决策与理由见 `01-项目骨架搭建方案.md` §2.1 |

## 二、分层架构设计

### 2.1 层次职责契约

| 层 | 允许做 | 禁止做 | 依赖方向 |
|---|---|---|---|
| **Presentation** | 渲染 UiState、收集用户事件、导航 | ❌ 直接调用 DAO/Repository；❌ 在 Composable 内做业务计算；❌ 持有 Context 引用超出生命周期 | → ViewModel |
| **ViewModel** | 组合 UseCase、维护 `StateFlow<UiState>`、处理用户意图 | ❌ 包含可复用的业务算法（应下沉 UseCase）；❌ 引用 Android View/Activity | → Domain（接口） |
| **Domain** | 纯 Kotlin 业务规则、跨 Repository 编排 | ❌ 引用 Android SDK；❌ 引用 Room 注解 | → Repository 接口 |
| **Data** | 持久化、事务、查询下推、DTO 映射 | ❌ 反向依赖 ViewModel；❌ 在 DAO 里写业务判断 | → Room / 平台 |
| **Platform** | 系统能力封装（WorkManager/MediaStore/网络） | ❌ 直接被 Composable 调用 | 被 Domain/Data 依赖 |

### 2.2 数据流（读路径）

```
SQLite ──Flow──> DAO ──Flow──> Repository ──Flow──> UseCase ──combine──> ViewModel
                                                                            │
                                                                    stateIn(Eagerly)
                                                                            │
                                                                     StateFlow<UiState>
                                                                            │
                                                                collectAsStateWithLifecycle
                                                                            │
                                                                        Composable
```

**关键约束 —— `stateIn` 一律 `SharingStarted.Eagerly`。**

这不是风格偏好，是**血的教训**：`TransactionViewModel.kt:87` 原用 `SharingStarted.WhileSubscribed(5000)`，导致账户余额在无订阅者的 5 秒窗口后停止上游收集，UI 恢复订阅时读到 `emptyMap()` 初值——表现为"账户余额恒显示 ¥0.00"。修复即改为 `Eagerly`（见 `BUGFIX_ROADMAP_budget_account.md` Bug 2）。

> 规则固化：使用 `WhileSubscribed` 必须在代码注释中论证「为何本流断开重连是安全的」，否则 Review 驳回。

### 2.3 数据流（写路径）

```
Composable 事件 → ViewModel.onXxx()
                    → viewModelScope.launch
                      → database.withTransaction {          ← ★ 多表写必须包事务
                            transactionRepo.insert(...)
                            tagRepo.setTransactionTags(...)
                        }
                    → Room 自动通知 Flow → UI 自动刷新（无需手动 refresh）
```

**关键约束 —— 多表写必须包 `withTransaction`。** 典型场景：新增一笔带标签的交易 = 写 `transactions` + 写 N 行 `transaction_tags`。不包事务时，中途崩溃会产生"交易存在但标签丢失"或更糟的孤儿关联。

### 2.4 依赖注入拓扑

```
databaseModule    : single  JianjiDatabase, 8×DAO
repositoryModule  : single  7×Repository（绑定到 domain 接口）
domainModule      : factory N×UseCase
viewModelModule   : viewModel 6×ViewModel
```

**当前偏差**：全部 22 个定义挤在单文件 `KoinModule.kt`(42 行)，且 `TransactionViewModelFactory.kt` 作为**第二条 DI 通道**残留。整改方案见 `01-项目骨架搭建方案.md` §5.1。

**依赖倒置的实际收益点**：`SettingsViewModel` 构造函数当前有 **9 个参数**，`TransactionViewModel` 有 6 个。若 Repository 不抽接口，单元测试必须 mock 具体类（需 `mockk(relaxed=true)` 且受 final 类限制）；抽接口后可用 Fake 实现，测试可读性与稳定性显著提升。

## 三、关键子系统设计

### 3.1 记账核心（Transaction）

| 要素 | 设计 |
|---|---|
| 金额表示 | **`Long` 分**（`amount_cents`）。展示 `/100.0`，输入 `Math.round(yuan*100)` |
| 类型 | `INCOME` / `EXPENSE` / `TRANSFER` |
| 删除 | **软删除**：`deleted_at` 非空即视为已删；所有列表/统计/汇总 SQL 均带 `deleted_at IS NULL` |
| 标签 | 多对多，经 `transaction_tags` 关联；与分类**正交** |

**转账（TRANSFER）的架构处理**是本子系统最特殊的一点：

- 转账**不**拆成两条流水，而是**单条记录 + `accountId`(转出) + `toAccountId`(转入)**
- 为满足 `categoryId` 外键非空约束，`MIGRATION_3_4` 插入了一条**系统分类**「转账」（`isSystem=1`），不在用户分类列表展示
- 余额计算时转账需**双边处理**：转出账户 `-amount`，转入账户 `+amount`
- 统计时转账**必须排除**，否则同一笔钱被计入支出，报表虚高

> 该设计的代价与替代方案辨析见 `03-核心业务建模与难点攻克报告.md` §难点 1。

### 3.2 预算子系统（Budget）

| 要素 | 设计 |
|---|---|
| 维度 | `categoryId` 为 `null` = 总预算；非空 = 分类预算 |
| 周期 | `MONTHLY`（用 `year`+`month`）/ `YEARLY`（用 `year`，`month` 忽略置 0） |
| 占用计算 | **不落库**，由「该周期内该分类的 `EXPENSE` 求和」实时算出 |
| 金额类型 | ⚠️ 仍为 `Double`（**唯一未随 `MIGRATION_6_7` 迁到 `Long` 分的金额字段**） |

**架构缺陷（P1 级）**：`Budget.amount: Double` 与 `Transaction.amountCents: Long` 单位/类型不一致。预算占用率 = `支出分/100.0 ÷ 预算Double`，两次浮点转换，在临界值（如 99.99% vs 100%）会产生"预算明明没超却提示超支"的观感 bug。整改方案见 `02b-数据库设计方案.md` §规划迁移 v7→v8。

### 3.3 账户子系统（Account）

**核心决策：账户余额不落库，动态计算。**

`MIGRATION_6_7` 已**移除 `accounts.balance` 列**。理由：

| 落库余额（旧） | 动态计算（现） |
|---|---|
| 每笔增删改都要同步更新余额，任一路径遗漏即数据不一致 | 余额永远等于流水之和，**结构性不可能不一致** |
| 软删除、导入、迁移都要额外维护余额 | 无需维护 |
| 读快 | 读需聚合（当前数据量下可接受） |

**代价与缓解**：数据量增大后 O(n) 聚合会拖慢首页。缓解手段按序：① `date`/`accountId` 索引（已有）；② SQL 下推 `SUM` 而非 Kotlin 侧遍历；③ 达到瓶颈再引入「月度快照表」增量累计。**当前不做 ③**——过早优化。

### 3.4 周期记账（Recurring）

| 要素 | 设计 |
|---|---|
| 存储 | `recurring_transactions` 表存**模板 + `nextRunDate`** |
| 频率 | `DAILY` / `WEEKLY` / `MONTHLY` / `YEARLY`，配 `interval`（每 N 个周期） |
| 触发 | 应用启动时查 `getDue(now)`（`nextRunDate <= now AND isActive=1`）→ 生成真实交易 → 推进 `nextRunDate` |
| 算法 | `RecurringSchedule.computeRecurringNextRun()`，已有 `RecurringScheduleTest` 覆盖 |

**架构风险**：触发依赖「用户打开 App」。用户 3 个月不开 App，再打开时需**一次性补记 3 个月的账**（catch-up）。补记的幂等性、批量事务、UI 提示是关键难点，详见 `03` 报告 §难点 2。

### 3.5 备份与恢复子系统（数据安全生命线）

```
┌─ 手动备份 ─────────────────────────────────────────┐
│ DataExportManager.generateExportJson()             │
│   → Gson 序列化全表（含已软删记录）                  │
│   → BackupStorage 写入 MediaStore Downloads        │
└────────────────────────────────────────────────────┘
┌─ 自动备份 ─────────────────────────────────────────┐
│ BackupScheduler → WorkManager PeriodicWork         │
│   → AutoBackupWorker → AutoBackup → BackupStorage  │
└────────────────────────────────────────────────────┘
┌─ 恢复 ─────────────────────────────────────────────┐
│ DataImportManager 解析 JSON → 校验 → 事务写入        │
│   （容错已由 ImportParsingToleranceTest 覆盖）       │
└────────────────────────────────────────────────────┘
```

**为什么写 MediaStore Downloads 而非应用私有目录**：备份的核心诉求是「**卸载 App 后仍可恢复**」。私有目录随卸载被清除，等于备份作废。

**由此推导出的加密方案约束**（见 `docs/backup-encryption-design.md`）：

- ❌ **Android Keystore 方案被否决**——Keystore 密钥随 App 卸载被系统销毁且不可导出，与"卸载后可恢复"的语义**自相矛盾**
- ✅ 采用 **用户口令 + PBKDF2WithHmacSHA256（≥120000 迭代，16B 随机盐）派生 AES-256 密钥 + AES/GCM/NoPadding（12B 随机 IV，128bit Tag）**
- 盐与 IV 明文存入文件头（不需保密）；迭代次数写入文件头以支持未来调参兼容
- **当前状态：核心加密能力已实现（v1.6.27 落地，v1.6.28 发布）。** `BackupCrypto`（PBKDF2+AES-GCM）+ `AutoBackup`/`DataImportManager` 透明加解密已上线，明文最高风险已消除。**剩余待办**：设置页口令输入框 UI 入口（见 `backup-encryption-design.md` §6），用户目前尚不能在界面启用加密口令。

**ProGuard 强耦合警告**：Gson 依赖「字段名反射 + 泛型签名」。R8 混淆后 `List<TransactionImport>` 元素类型会绑定错误类，抛 `p6.n cannot be cast to z5.h`（**仅 release 混淆包出现**）。现靠 `-keep class com.example.jianji.{data,utils}.** { *; }` 兜住。**任何涉及 DTO 包结构的改动，都必须以 release 变体真机回归为验收，debug 包测不出来。**

### 3.6 统计子系统

| 要素 | 设计 |
|---|---|
| 计算 | `StatisticsCalculator`（纯函数，已有 `StatisticsCalculatorTest`） |
| 渲染 | MPAndroidChart v3.1.0（View 体系，经 `AndroidView` 桥接进 Compose） |
| 数据源 | `getByDateRangeSnapshot()` 一次性快照，非 Flow |

**风险**：MPAndroidChart 来自 jitpack（`com.github.PhilJay:MPAndroidChart:v3.1.0`），源可用性不受控；且 View/Compose 混合渲染在主题切换、深色模式下需手动同步样式。新增图表类型前应先评估 Compose Canvas 自绘。

### 3.7 桌面小组件（Glance）

Glance AppWidget 1.1.0，`JianjiWidget` + `JianjiWidgetReceiver`。

**约束**：Widget 进程与主进程独立，**不得在 Widget 内做全表扫描或复杂聚合**——Widget 更新有严格的 ANR 预算。应只读预聚合结果。

### 3.8 更新检查

`UpdateManager`(402 行) + `VersionComparator`（已有测试）。拉取 GitHub Releases API 比对 `versionName`。这是**全应用唯一的网络出口**。

## 四、跨切面设计

### 4.1 线程模型

| 场景 | Dispatcher | 说明 |
|---|---|---|
| DAO `suspend`/`Flow` | Room 内建线程池 | **不要**再套 `withContext(IO)`（重复切换） |
| 备份/导出/海报/文件 IO | `Dispatchers.IO` | 显式声明 |
| 统计聚合 | `Dispatchers.Default` | CPU 密集 |
| UI 状态 | `viewModelScope`（Main） | 禁止 `GlobalScope` |

### 4.2 错误处理策略

| 层 | 策略 |
|---|---|
| Data | 抛出，不吞。Room 异常向上传递 |
| Domain | 转换为领域错误类型（`Result` 或 sealed error） |
| ViewModel | catch → `Timber.e(e, ...)` → 写入 `UiState.error` |
| UI | **必须**给用户可见反馈 |

**反面教材（已发生）**：`BudgetSettingsDialog` 在 `budgetVM == null` 时静默不保存，用户看到的是"我明明设置了预算，首页却恒为 0"。根因是 `JianjiApp.kt:264` 漏传 `budgetVM=` 参数——**一个可选参数 + 一次静默降级 = 一个用户无法自查的 bug**。规则：可选依赖为 null 时，要么给可见反馈，要么直接崩在开发期。

### 4.3 日志

Timber 5.0.1 为**唯一**日志出口。禁止 `println` / `android.util.Log` / 静默 `catch {}`。备份口令、密钥绝不入日志。

### 4.4 安全与隐私

| 项 | 现状 | 风险等级 |
|---|---|---|
| DB 加密 | ❌ 无（明文 SQLite，仅靠应用沙箱） | 中（root 设备可读） |
| 备份加密 | ❌ 无（明文 JSON 在共享 Downloads） | **高** |
| 网络 | 仅 GitHub Releases（HTTPS，只读） | 低 |
| 权限 | 存储（MediaStore）、通知（备份结果） | 低 |
| 数据外发 | 无埋点、无三方 SDK、无广告 | 低（架构优势） |

### 4.5 构建与交付

| 项 | 约定 |
|---|---|
| 构建 | **必须 GitHub Actions CI，禁止本地构建**；编译验证以 CI 为准 |
| 触发 | `push main` / `tag v*` / PR / `workflow_dispatch` |
| 签名 | CI 环境变量 `KEYSTORE_FILE` / `KEY_STORE_PASSWORD` / `KEY_ALIAS` / `KEY_PASSWORD`；debug 与 release 同签名以支持覆盖安装 |
| 混淆 | release `isMinifyEnabled=true` + `isShrinkResources=true` |
| 发布 | tag push 触发 release；**重发同版本必须先 `DELETE /releases/{id}`**，否则 workflow 守卫会跳过创建 |

## 五、质量属性与架构决策记录

### 5.1 质量属性优先级

| 属性 | 优先级 | 架构支撑 | 当前达成度 |
|---|---|---|---|
| **数据完整性** | P0 | `Long` 分金额、外键 CASCADE、软删除、事务、迁移链 | 🟡 迁移测试与 schema 基线缺位 |
| **升级安全性** | P0 | 6 条 Migration、`fallbackToDestructiveMigration` 仅用于降级 | 🟡 无 Migration 测试 |
| 可维护性 | P1 | MVVM、Koin、Repository | 🟠 无 domain 层、utils 杂物袋、8 个巨型文件 |
| 隐私安全 | P1 | 无网络外发 | 🔴 备份明文落共享目录 |
| 性能 | P2 | 4 个索引、SQL 下推 SUM | 🟢 当前量级充足 |
| 可测试性 | P2 | 纯函数 Calculator | 🔴 5 个测试文件，DAO/VM/Migration 全空 |

### 5.2 架构决策记录（ADR）

| ID | 决策 | 备选 | 理由 | 代价 |
|---|---|---|---|---|
| ADR-1 | 金额用 `Long` 分 | `Double` / `BigDecimal` | 消除浮点累积误差（尤其 SUM 与转账对账）；`BigDecimal` 在 Room/Gson 中成本高 | 需一次性重建三张表（`MIGRATION_6_7` 已付） |
| ADR-2 | 账户余额动态计算，删除 `balance` 列 | 落库 + 增量维护 | 结构性杜绝不一致 | 读取需聚合 |
| ADR-3 | 转账用单条记录 + `toAccountId` | 拆两条流水 | 语义完整、编辑/删除原子 | 统计需显式排除；需系统分类兜外键 |
| ADR-4 | 软删除（`deleted_at`）+ 回收站 | 硬删除 + 撤销栈 | 支持跨会话恢复 | 所有查询必须带 `deleted_at IS NULL`（**漏一处即数据泄漏到报表**） |
| ADR-5 | 备份写共享 Downloads | 应用私有目录 | 卸载后可恢复 | 明文暴露 → 必须尽快加密 |
| ADR-6 | 备份加密用口令 PBKDF2，**否决 Keystore** | Android Keystore AES-GCM | Keystore 密钥随卸载销毁，与备份语义矛盾 | 用户需记住口令；忘记 = 备份作废 |
| ADR-7 | 单模块 | 多模块 | 10112 行 / 单人维护，多模块成本 > 收益 | 靠约定而非编译期约束 |
| ADR-8 | `stateIn(Eagerly)` | `WhileSubscribed` | 避免余额/预算读到初值（已发生 bug） | 略增内存与后台收集开销 |
| ADR-9 | Koin | Hilt | 轻量、无 KAPT、Kotlin DSL；项目已有 KSP（Room）不宜再叠 | 无编译期校验，错误在运行时暴露 |
| ADR-10 | `fallbackToDestructiveMigration` 保留 | 关闭 | 防止版本回退时 Room 拒绝降级导致闪退 | **必须**配合"每次升级都写 Migration"的纪律，否则会静默清库 |

> ⚠️ ADR-10 是**双刃剑**：它的存在意味着「忘写 Migration」不会在开发期崩溃，而是**静默清空用户数据**。这使得 §六 R2 的迁移测试从"锦上添花"变为"必需品"。

### 风险处置优先级

```
P0（下个迭代必做）：R2（迁移测试+schema入库）→ R1（备份加密）
P1（两个迭代内）  ：R3（序列化收敛）→ R4（软删过滤统一）→ R5（Budget 金额）
P2（持续演进）    ：R7（domain 层）→ R8（拆巨型文件）→ R9（删 Factory）
P3（观察）        ：R6 / R10 / R11
```

**排序理由**：R2 排第一不是因为它最"可怕"，而是因为它**同时是其他所有整改的安全网**——没有迁移测试，R5（改 Budget 字段）、R3（改 DTO 包）这些动数据的整改都不敢做。先修安全网，再做手术。
