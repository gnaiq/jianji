## 零、核心业务域全景

### 0.1 领域划分

| 域 | 核心概念 | 复杂度 | 主要风险 |
|---|---|---|---|
| **记账** | Transaction / 三种 type / 金额分 | ★★★★ | 转账语义、金额精度 |
| **账户** | Account / 动态余额 | ★★★ | 一致性 vs 性能 |
| **预算** | Budget / 占用率 / 超支 | ★★★ | 类型不一致、重复行 |
| **周期记账** | Recurring / nextRunDate / catch-up | ★★★★★ | 补记正确性、双实现漂移 |
| **分类** | Category 两级树 / 系统分类 | ★★★ | 删除级联、树深度 |
| **标签** | Tag 多对多 | ★★ | 与软删的交互 |
| **回收站** | deleted_at 软删 | ★★★ | 过滤穿透 |
| **备份恢复** | JSON DTO / 加密 / 兼容 | ★★★★★ | 数据契约、ProGuard、明文 |
| **统计** | 聚合 / 图表 | ★★★ | 转账污染、浮点 |

### 0.2 核心业务不变式（Invariants）

这 8 条是**任何改动都不得破坏**的业务铁律：

| ID | 不变式 | 当前保障方式 |
|---|---|---|
| I-1 | 账户余额 ≡ 该账户所有未删交易的净和 | 结构性（不落库） |
| I-2 | 转账不改变账户总资产 | 结构性（单条记录双边） |
| I-3 | 转账不得计入收入或支出统计 | 依赖 `type` 过滤 |
| I-4 | 已软删交易不得出现在任何统计/汇总/列表中 | 每条 SQL 手写 `deleted_at IS NULL` |
| I-5 | 同一周期同一分类只能有一条预算 | 应用层 upsert（**无 DB 约束**） |
| I-6 | 周期任务在同一个 occurrence 上只能生成一笔交易 | `nextRunDate` 原子推进 |
| I-7 | 金额在存储与计算全链路不得产生浮点误差 | `amount_cents: Long`（**budgets 除外**） |
| I-8 | 备份文件必须能被同版本及后续版本完整恢复 | DTO 兼容 + 容错解析 |

> 后续每个难点的分析，都是在追问：**这条不变式，在什么边界下会被打破？**

## 难点 1：转账建模（单条记录还是双分录）

### 1.1 业务语义

用户从「招行卡」转 1000 元到「支付宝」。这笔操作：
- **不是**收入，**不是**支出——总资产不变
- 但两个账户余额必须各自变化
- 用户期望在流水里看到**一条**「转账」记录，而不是两条

### 1.2 现实现

**存储**：单条 `Transaction`，`type=TRANSFER`，`accountId`=转出，`toAccountId`=转入，`categoryId` 指向系统分类「转账」（`isSystem=1`，`MIGRATION_3_4` 插入）。

**余额计算**（`TransactionViewModel.accountBalances`，实测）：
```kotlin
TransactionType.TRANSFER -> {
    add(t.accountId, -t.amountCents / 100.0)     // 转出 -
    add(t.toAccountId, t.amountCents / 100.0)    // 转入 +
}
```

**统计排除**（`StatisticsCalculator.calculatePeriodStatistics`，实测）：
```kotlin
val incomeTransactions  = transactions.filter { it.type == TransactionType.INCOME }
val expenseTransactions = transactions.filter { it.type == TransactionType.EXPENSE }
```
✅ **白名单过滤**（只取 INCOME / EXPENSE），TRANSFER 天然被排除。这比黑名单 `filter { it.type != TRANSFER }` 更健壮——未来新增 type 时不会意外混入。

### 1.3 方案辨析：为何不用双分录（复式记账）

| 维度 | 单条 + toAccountId ✅ 现方案 | 双分录（拆两条 + pairId） |
|---|---|---|
| 流水展示 | 天然一条 | 需按 `pairId` 合并渲染 |
| 编辑/删除原子性 | 天然原子 | 必须双条同步，漏一条即资产凭空增减（**违反 I-2**） |
| 统计排除 | 一次 type 过滤 | 两条都要排除，漏一条即报表虚高 |
| 余额计算 | 一次遍历双边处理 | 天然正确 |
| 会计规范性 | 非标准复式 | 标准复式 |
| 扩展到多币种/手续费 | 需加列 | 天然支持 |

**结论：现方案正确。** 个人记账的核心诉求是「流水直观 + 不出错」，不是会计合规。双分录把一个**结构性保证**（单条记录不可能不平）降级成了**流程性保证**（两条记录靠代码保持同步），在没有服务端校验的单机应用上是风险放大。

### 1.4 边界枚举与缺陷

| # | 边界场景 | 现行为 | 判定 |
|---|---|---|---|
| B1-1 | 转账到同一账户（`accountId == toAccountId`） | 余额 `-x` 后 `+x` = 净 0，但产生一条无意义流水 | 🟡 应在 UI 层禁止 |
| B1-2 | `toAccountId` 为 null 的 TRANSFER | `add(null, ...)` 直接 return，钱**凭空消失**（转出账户 -x，无处 +x）→ **违反 I-2** | 🔴 缺陷 |
| B1-3 | 删除转入账户 | `clearToAccount()` 置 NULL → 退化为 B1-2，资产凭空减少 | 🔴 缺陷 |
| B1-4 | 用户手动把系统「转账」分类删掉 | `transactions.categoryId` 有 CASCADE → **所有转账记录被连带删除** | 🔴 严重缺陷 |
| B1-5 | 转账记录被软删 | 余额计算基于 `transactions` Flow（已过滤软删），双边同时失效 | ✅ 正确 |
| B1-6 | 备注搜索/标签筛选命中转账 | 会出现在列表中 | ✅ 合理 |

### 1.5 攻克方案

| 缺陷 | 方案 | 验收标准 |
|---|---|---|
| B1-2 | ① UI 层：`type=TRANSFER` 时 `toAccountId` 为必填，未选不允许保存；② 数据层：`insertTransaction` 前 `require(type != TRANSFER \|\| toAccountId != null)`；③ 余额计算发现 TRANSFER 且 `toAccountId == null` 时 `Timber.e` 告警 | 单测：构造 `TRANSFER + toAccountId=null` → 保存被拒 |
| B1-3 | 删除账户前检查：若该账户是任何转账的 `toAccountId`，弹窗告知「将有 N 笔转账失去转入方」，提供「改指到其他账户 / 取消」，**禁止静默置 NULL** | 手工：建转账→删转入账户→确认有阻断提示 |
| B1-4 | ① `CategoryRepository.delete()` 前置 `require(!category.isSystem)`；② 分类管理 UI 已按 `isSystem=1` 过滤，需**同时**校验数据层（防导入/恢复路径绕过） | 单测：删除 `isSystem=1` 分类抛异常 |
| B1-1 | UI 层同账户转账置灰保存按钮 | 手工验证 |

> **B1-4 是本报告发现的最高危缺陷**：一次误删就 CASCADE 掉用户全部转账历史，且**不可撤销**（CASCADE 是硬删，不进回收站）。

## 难点 2：周期记账 catch-up（长期未开 App 的补记）

### 2.1 业务语义

用户设了「每月 1 号房租 3000」。3 个月没打开 App，第 4 个月打开时，应当补记 3 笔房租，日期分别是各月 1 号（**不是**全记在打开当天）。

### 2.2 现实现（`TransactionViewModel.processRecurringDue()`，实测）

```kotlin
val now = LocalDateTime.now()
val due = recurringRepo.getDue(now)              // nextRunDate <= now AND isActive = 1
database.withTransaction {                        // ★ 整批包事务
    for (rtx in due) {
        val occurrences = mutableListOf<LocalDateTime>()
        var cur = rtx.nextRunDate
        var guard = 0
        while (cur <= now && guard < 1000) {       // ★ 展开所有错过的 occurrence
            occurrences.add(cur)
            cur = nextRunAfter(cur, rtx)
            guard++
        }
        occurrences.forEach { date ->
            transactionRepository.insertTransaction(
                Transaction(..., date = date, ...)  // ★ 用 occurrence 日期，不是 now
            )
        }
        var next = rtx.nextRunDate
        while (next <= now) next = nextRunAfter(next, rtx)
        if (next != rtx.nextRunDate) recurringRepo.update(rtx.copy(nextRunDate = next))
    }
}
```

### 2.3 评价：核心逻辑是正确的

三个关键点都做对了，值得肯定：

| 点 | 实现 | 意义 |
|---|---|---|
| 补记而非合并 | `while (cur <= now)` 展开全部 occurrence | 3 个月生成 3 笔，符合语义 |
| 日期归属正确 | `date = occurrence`，非 `now` | 报表按月归属正确 |
| **原子性** | 整个循环包在 `withTransaction` 内 | 生成交易与推进 `nextRunDate` 同生共死，**满足 I-6**，不会重复记账 |
| 死循环防护 | `guard < 1000` | 防止 `nextRunAfter` 返回不递增值时卡死 |

### 2.4 但存在 4 个实质缺陷

#### 🔴 D2-1：两套下次执行时间算法并存，且语义不同

| 算法 | 位置 | 签名 | 基准 |
|---|---|---|---|
| `computeRecurringNextRun()` | `utils/RecurringSchedule.kt` | 纯函数，有单测 | 基于 **`now`** |
| `nextRunAfter()` | `TransactionViewModel.kt` **private** | 无单测 | 基于 **`prev`（上次 occurrence）** |

`RecurringDialog.kt:152/178` 用前者算「创建时的首次 nextRunDate」与预览；`processRecurringDue()` 用后者做递推。

**为什么这是缺陷**：两者对同一配置可能给出不同结果。实测差异：

| 场景 | `computeRecurringNextRun` | `nextRunAfter` |
|---|---|---|
| WEEKLY | 先对齐到 `dayOfWeek`，再 `plusWeeks(iv-1)` | 直接 `prev.plusWeeks(iv)`，**完全不看 `dayOfWeek`** |
| MONTHLY 月末钳制 | `min(dayOfMonth, 当月天数)` | 同逻辑（`if dom > lengthOfMonth`） |
| DAILY | `now.plusDays(iv).atStartOfDay()` | `prev.plusDays(iv).atStartOfDay()` |
| YEARLY | 用 `monthOfYear` | （需核对，`nextRunAfter` 的 YEARLY 分支未在本次截取范围内完整可见） |

**WEEKLY 的差异是真实 bug**：若首次 `nextRunDate` 因某种原因不落在 `dayOfWeek` 上（如用户改了配置但未重算），`nextRunAfter` 会一直沿着错误的星期几递推，**永远不会自我纠正**。

#### 🟠 D2-2：`processRecurringDue()` 的调用时机与并发

该方法在 `TransactionViewModel` 中，触发点依赖 UI 层调用。风险：
- 若在 Composable 中被调用且未做 `LaunchedEffect(Unit)` 约束，可能随重组**多次触发**
- 虽然事务保证了单次执行的原子性，但**两次并发调用**都可能读到同一个 `due` 列表（读发生在 `withTransaction` 之外！`getDue(now)` 在事务块前调用），产生**重复记账 → 违反 I-6**

> 注意这个细节：`val due = recurringRepo.getDue(now)` 在 `database.withTransaction {}` **之外**。事务只保护了写，没保护「读-改-写」的完整区间。

#### 🟡 D2-3：`guard < 1000` 静默截断

DAILY 频率停用 3 年 = 1095 次 > 1000，会**静默少记 95 笔**，且用户无任何感知。

#### 🟡 D2-4：批量补记无用户感知

一次性插入几十上百笔交易，用户打开 App 看到流水暴增，无提示、无确认、无法整批撤销。

### 2.5 攻克方案

| 缺陷 | 方案 | 验收标准 |
|---|---|---|
| **D2-1** | 统一为**一个**纯函数 `nextRunAfter(prev, config)`，放 `domain/usecase/recurring/`。`computeRecurringNextRun(now, config)` 改为其薄封装（首次计算 = 以 `now` 为 `prev` 求下一个 ≥now 的 occurrence）。删除 ViewModel 里的 private 副本 | 单测覆盖 4 种频率 × {月末 29/30/31、闰年 2/29、interval>1、跨年}；**特别断言 WEEKLY 递推始终落在配置的 `dayOfWeek` 上** |
| **D2-2** | ① 把 `getDue()` **移进** `withTransaction` 块内，让读-改-写在同一事务；② 调用点用 `LaunchedEffect(Unit)` 或 Application 级单次触发；③ 加进程内 `Mutex` 防并发重入 | 单测：并发调用两次 `processRecurringDue()`，断言生成交易数 = 期望 occurrence 数（不翻倍） |
| **D2-3** | 保留 guard 但**不静默**：截断时 `Timber.w` + 在 UiState 暴露「有 N 笔未补记」提示 | 单测：构造 1500 次 occurrence，断言有警告产出 |
| **D2-4** | 补记完成后 Snackbar：「已为你补记 N 笔周期账目」，点击跳转到按 `createdAt` 排序的筛选视图 | 手工验证 |

### 2.6 建议新增：`lastGeneratedDate` 幂等键

即使 D2-2 修复，`nextRunDate` 单游标模式仍有理论风险（如用户手动改系统时间回退）。建议 v8 迁移增列 `lastGeneratedDate`，生成前判重。**优先级 P3**——先修 D2-2，观察是否还有实际问题。

## 难点 3：账户余额的一致性与性能

### 3.1 业务语义

余额必须**永远**等于流水净和（I-1）。用户最不能容忍的是「余额和流水对不上」。

### 3.2 现实现（实测）

`accounts.balance` 列已在 `MIGRATION_6_7` 删除。余额由 `TransactionViewModel.accountBalances` 从**全量** `transactions` Flow 遍历计算，`stateIn(Eagerly)`。

### 3.3 关键设计决策的完整因果链（重要）

代码注释里保留了一段血案记录，值得完整还原，因为它揭示了一个**架构级陷阱**：

```
SettingsScreen / JianjiApp 的账户弹窗
  → 以 accountBalances.value 快照方式读取
    → 读 .value 不构成 Flow 订阅
      → 若 stateIn 用 WhileSubscribed，上游在无订阅者时不启动收集
        → .value 恒为初始值 emptyMap()
          → 账户余额全部显示 ¥0.00
```

**这个 bug 的可怕之处在于**：它不是逻辑错误，代码"看起来完全正确"；它只在特定的**读取方式（`.value` 快照）× 特定的共享策略（`WhileSubscribed`）** 组合下暴露。修复是一行 `Eagerly`，但发现它需要理解 `StateFlow` 的冷/热语义。

**沉淀为团队规则**：
> 任何 `StateFlow` 若存在 `.value` 快照读取方，其 `stateIn` **必须** `Eagerly`。要用 `WhileSubscribed`，必须先证明所有消费方都是 `collect` 订阅。

现代码中该 `Eagerly` 还兼任上游 `transactions`(`WhileSubscribed`) 的常驻订阅者——这是个隐式依赖，注释已写明，**改动时不可拆**。

### 3.4 边界与缺陷

| # | 场景 | 现行为 | 判定 |
|---|---|---|---|
| B3-1 | `accountId = null` 的交易（无账户流水） | `add()` 直接 return，不计入任何账户 | ✅ 正确 |
| B3-2 | 账户被删，交易 `accountId` 置 NULL | 该笔金额从所有账户余额中消失，但总收支统计仍含它 | 🟡 语义歧义：钱去哪了？ |
| B3-3 | 万级交易量 | 每次 Flow 发射都全量遍历 | 🟡 性能 |
| B3-4 | 余额计算用 `Double` | `t.amountCents / 100.0` 逐笔转 Double 再累加 → **违反 I-7** | 🔴 精度缺陷 |

**B3-4 详解**：`amountCents / 100.0` 在**每一笔**上做整数→浮点转换，然后累加。0.01+0.02≠0.03 类误差会在万笔量级累积到分位可见。正确做法是**先用 `Long` 累加分，最后一次除 100**：

```kotlin
// ❌ 现状
map[accId] = (map[accId] ?: 0.0) + t.amountCents / 100.0

// ✅ 应改为
val map = mutableMapOf<Long, Long>()          // 累加分
map[accId] = (map[accId] ?: 0L) + t.amountCents
// 展示层：balanceCents / 100.0
```

同样问题存在于 `StatisticsCalculator`：`txns.sumOf { it.amountCents / 100.0 }` —— 应改为 `txns.sumOf { it.amountCents } / 100.0`。**一个括号的位置，决定了 I-7 是否成立。**

### 3.5 攻克方案

| 缺陷 | 方案 | 验收标准 |
|---|---|---|
| **B3-4** | 全链路整数分累加，仅展示层除 100。涉及 `accountBalances`、`StatisticsCalculator` 全部 `sumOf`、DAO 的 `SUM(amount_cents)/100.0`（改返回 `Long?`） | 单测：10000 笔 `amountCents=1`（1 分）求和，断言 `== 100.00` 精确相等 |
| B3-2 | 引入虚拟「未分配」账户视图，展示无账户流水合计，让钱有去处 | 手工验证 |
| B3-3 | 达到瓶颈前不优化。触发阈值：首页加载 >300ms。届时按 `02-总体架构设计方案.md` ADR-2 的缓解手段 ②③ 推进 | 性能埋点 |

## 难点 4：预算占用与超支判定

### 4.1 业务语义

用户设「本月餐饮预算 800」，App 需实时显示「已用 650 / 800（81%）」，超支时告警。

### 4.2 现实现

- `Budget` 存 `amount: Double` + `period` + `year` + `month` + `categoryId`(null=总预算)
- 占用**不落库**，`TransactionRepository.getBudgetProgress(year, month, budget, categoryId)` 实时算
- `BudgetDao.upsertBudget()` 用 `@Transaction` 保证 upsert 原子性

### 4.3 缺陷

#### 🔴 D4-1：`Budget.amount` 是唯一的 `Double` 金额

全库金额已统一 `Long` 分（`MIGRATION_5_6`/`6_7`），**只有 `budgets.amount` 例外**。占用率 = `(支出分 → Double) / (预算 Double)`，双重浮点。

**用户可感知的表现**：预算 0.1+0.2 类场景下，花了正好 800.00 却显示 100.01%，弹出"已超支"——**用户会认为 App 算错账**。这在记账类 App 中是信任级问题。

#### 🔴 D4-2：`(categoryId, year, month, period)` 无唯一索引

`upsertBudget()` 是「先查后插」的应用层 upsert。若因导入恢复、并发或历史数据产生了重复行：
- `getCategoryBudget(...) LIMIT 1` 会**静默取到其中一条**
- 用户改预算改的是 A 行，界面读的是 B 行 → **"改了没生效"**

这类 bug 极难排查，因为代码逻辑完全正确，问题在数据。

#### 🟠 D4-3：`categoryId` 无外键，删分类留孤儿预算

删除餐饮分类后，`budgets` 中该 `categoryId` 的行永久残留，`getForMonth()` 会返回一条无法解析分类名的预算。

#### 🟡 D4-4：分类预算与总预算的关系未定义

若总预算 3000，各分类预算之和 5000，业务语义是什么？现无校验、无提示。

#### 🟡 D4-5：子分类预算的归属未定义

`categories` 支持两级（`parentId`）。给父分类「餐饮」设预算，子分类「外卖」的支出是否计入？现实现按 `categoryId` 精确匹配 → **不计入**。这大概率不符合用户直觉。

### 4.4 攻克方案

| 缺陷 | 方案 | 验收标准 |
|---|---|---|
| **D4-1** | v7→v8 迁移 `amount REAL → amount_cents INTEGER`（`CAST(ROUND(amount*100) AS INTEGER)`），占用率改整数比较：`usedCents >= budgetCents` | 单测：预算 80000 分、支出 80000 分 → 占用率**精确** 100.0%，不触发超支；支出 80001 分 → 触发 |
| **D4-2** | 迁移中**先去重**（保留 MAX(id)）**再**建唯一索引 `(categoryId, year, month, period)`，DAO 改 `OnConflictStrategy.REPLACE` 真 upsert | 迁移测试：构造 3 条重复预算 → 迁移后剩 1 条且为最新；重复插入不报错 |
| **D4-3** | 迁移中补 `FOREIGN KEY(categoryId) REFERENCES categories(id) ON DELETE CASCADE` | 单测：删分类 → 其预算行同步消失 |
| D4-4 | 设置分类预算时，若总和超总预算，给**提示不阻断**（用户可能故意） | 手工验证 |
| D4-5 | 明确产品语义。**建议：父分类预算 = 自身 + 全部子分类支出之和**（更符合直觉），实现为 `categoryId IN (:id, SELECT id FROM categories WHERE parentId = :id)` | 单测：父分类预算下，子分类支出被计入 |

> ⚠️ D4-2 的迁移**必须先去重再建索引**。若存量已有重复行，直接建唯一索引会抛异常，导致**升级用户启动即崩**——这是比原 bug 严重得多的事故。

## 难点 5：软删除的语义穿透

### 5.1 业务语义

删除是"扔进回收站"，可恢复。已删记录**不得**出现在任何面向用户的数字里（I-4）。

### 5.2 现实现

`deleted_at` 时间戳。`TransactionDao` 中每条查询**手写** `deleted_at IS NULL`。三个刻意的例外：`getById()`（恢复需读到）、`getDeletedTransactions()`（就是查回收站）、`getAllIncludingDeletedSnapshot()`（备份需含已删）。

### 5.3 核心风险：这是纯人工纪律，无任何编译期保护

`transactions` 表现有 20+ 条查询，每条都靠开发者记得写这个条件。**漏写不会报错、不会崩溃**，只会让用户看到一个略微偏大的数字——而用户很可能**永远发现不了**，只是隐约觉得"账对不上"。

这是本项目**最隐蔽**的一类风险：不是崩溃，是**静默的数据失真**。

### 5.4 边界与缺陷

| # | 场景 | 现行为 | 判定 |
|---|---|---|---|
| B5-1 | 软删交易的标签关联 | `transaction_tags` 行仍在（CASCADE 只对硬删生效） | 🟠 `getTransactionsByTagIds()` **必须**自带 `deleted_at IS NULL`，否则回收站内容出现在标签筛选中 |
| B5-2 | 软删转账 | 双边余额同时失效 | ✅ 正确 |
| B5-3 | 回收站保留期 | 无自动清理，`purgeDeleted()` 需手动触发 | 🟡 长期积累占用空间 |
| B5-4 | 恢复的交易，其分类/账户已被删 | `categoryId` 悬空（分类硬删 CASCADE 会连带删掉软删记录本身）；`accountId` 已被 `clearAccount()` 置 NULL | 🟠 恢复出来的交易可能"缺胳膊少腿" |
| B5-5 | 备份含已删记录，恢复后回收站内容保留 | ✅ 设计正确 | ✅ |
| B5-6 | 硬删分类 → CASCADE → 软删的交易被真删 | 用户以为在回收站的记录**永久消失** | 🔴 缺陷 |

**B5-6 详解**：`transactions.categoryId` 是 `ON DELETE CASCADE`。用户删掉一个分类，该分类下**包括已在回收站的**交易全部被物理删除，不可恢复。用户的心智模型是"回收站里的东西是安全的"，实际不是。

### 5.5 攻克方案

| 缺陷 | 方案 | 验收标准 |
|---|---|---|
| **纪律问题** | ① 在 `TransactionDao` 文件头写死规约注释；② PR 模板加勾选项「新增 transactions 查询是否明确了软删过滤」；③ 考虑加 Room `@DatabaseView` 定义 `active_transactions` 视图，新查询一律基于视图 | Review 清单生效 |
| **B5-6** | 删除分类前检查该分类下交易数（**含软删**），非 0 时弹窗：「该分类下有 N 笔记录（含回收站 M 笔），删除后将永久丢失」，提供「迁移到其他分类」选项 | 手工：软删一笔 → 删其分类 → 确认有阻断提示 |
| B5-1 | 审计 `getTransactionsByTagIds()` 确认已带过滤（实测 SQL 需逐条核对） | SQL 走查 |
| B5-3 | 设置项「回收站保留 30 天」，`AutoBackupWorker` 顺带清理 | 手工验证 |
| B5-4 | 恢复时若 `accountId` 为 NULL，提示用户重新指定 | 手工验证 |

## 难点 6：备份恢复的数据契约

### 6.1 业务语义

**这是全应用最高价值的功能。** 没有服务端，备份是用户数据的**唯一**保险。备份失败或恢复错误 = 数据永久丢失。

### 6.2 现实现

```
导出：DataExportManager.generateExportJson() → Gson 序列化全表（含软删）
      → BackupStorage → MediaStore Downloads（共享目录，卸载不删）
自动：BackupScheduler → WorkManager PeriodicWork → AutoBackupWorker → AutoBackup
恢复：DataImportManager 解析 → 校验 → 事务写入（ImportParsingToleranceTest 覆盖容错）
```

### 6.3 三个结构性难点

#### 🔴 P6-1：明文落共享目录（最高安全风险）

任何有存储权限的 App 都能读到用户**全部**账目。这不是"可能的风险"，是**当前既成事实**。

**为什么不能简单用 Android Keystore 加密**——`docs/backup-encryption-design.md` 的这段推理是全项目最精彩的设计分析，值得原样保留：

> Keystore 密钥**随 App 卸载被系统销毁**且不可导出。而备份的核心诉求恰恰是「**卸载后仍可恢复**」。卸载 → 密钥没了 → 重装后无法解密旧备份 → **备份等于作废**。方案与目标自相矛盾。

**正确方向**：密钥不依赖设备/安装态，而是**从用户口令派生**。
- `PBKDF2WithHmacSHA256`，迭代 ≥120000（写入文件头以支持未来调参兼容）
- 随机 16B salt（明文存头，盐不需保密）
- `AES/GCM/NoPadding`，随机 12B IV，128bit Tag（同时保证机密性与防篡改）

**代价必须向用户明示**：忘记口令 = 备份永久作废，无任何找回途径。这个代价是**口令派生方案的本质属性**，不是缺陷——但必须在 UI 上说清楚，否则用户会在最需要恢复的时刻崩溃。

#### 🔴 P6-2：Gson + R8 的强耦合

Gson 依赖「字段名反射 + 泛型签名」。R8 混淆后 `List<TransactionImport>` 的元素类型绑定到错误类，抛 `p6.n cannot be cast to z5.h`。

**这个 bug 的恶性程度**：
- **只在 release 混淆包出现**，debug 包 100% 测不出来
- 表现为恢复功能崩溃 —— **恰好是用户数据最危险的时刻**
- 现靠 `-keep class com.example.jianji.{data,utils}.** { *; }` 兜住，代价是这两个包完全放弃混淆与裁剪

**衍生的强约束**：任何涉及 DTO 包结构的重构（如 `01` 方案中把 `utils/` 拆成 `core/*`），**必须**同步改 ProGuard 并以 **release 变体真机回归**为验收。这条约束把一次普通的包重命名变成了高风险操作。

#### 🟠 P6-3：备份格式版本兼容

老版本导出的 JSON 必须能被新版本恢复。数据模型已经历 `amount REAL → amount_cents`、`accounts.balance` 移除、标签系统新增等**破坏性变更**。

现有 `ImportParsingToleranceTest` 覆盖了解析容错，但需明确回答：
- v1.6.0 时代（金额 Double、无标签、有 balance）的备份文件，v1.6.26 能否恢复？
- 恢复时 `amount: 12.34` 如何转 `amountCents`？是否与 `MIGRATION_5_6` 的 `ROUND(amount*100)` 一致？
- 备份 JSON 里是否有 `schemaVersion` 字段用于分支处理？

### 6.4 攻克方案

| 难点 | 方案 | 验收标准 |
|---|---|---|
| **P6-1** | ① 立即：设置页明示「备份文件未加密，存放于下载目录」风险文案；② 落地口令加密（PBKDF2+AES-GCM），加密为**可选**开关，默认开启但允许关闭（兼容老用户）；③ UI 强提示「忘记口令则备份无法恢复」 | 单测：加密→解密往返一致；错误口令抛认证失败而非静默产出乱码；文件头可解析迭代次数 |
| **P6-2** | 三步收敛到 kotlinx-serialization：冻结（新代码禁用 Gson）→ 双写过渡（导出用 kotlinx，导入先试 kotlinx 后回退 Gson）→ 摘除 Gson 与两条 `-keep` | 每步以 **release 变体 CI + 真机"导出→卸载重装→导入"** 为验收 |
| **P6-3** | ① 备份 JSON 顶层增 `schemaVersion` 与 `appVersion`；② 建立**历史备份样本库**（v1.6.0 / v1.6.6 / v1.6.26 各一份，入库到 `androidTest/assets`）；③ 每份样本一个恢复回归测试 | androidTest：3 份历史样本全部恢复成功，逐表断言记录数与金额 |

> **建议把「历史备份样本库」作为常设资产**。每次发大版本，导出一份当版备份存入 `androidTest/assets/backup_samples/`。这是**唯一**能防住"新版本读不了老备份"这类灾难的手段，成本极低，收益极高。

## 难点 7：分类树与系统分类

### 7.1 现实现

- 两级树：`parentId = 0` 为一级，非 0 指向父分类（`isMajor get() = parentId == 0L`）
- 系统分类：`isSystem = 1`（如「转账」），不在用户列表展示
- `transactions.categoryId` → `categories.id` **ON DELETE CASCADE**

### 7.2 缺陷

| # | 问题 | 判定 |
|---|---|---|
| B7-1 | 用 `parentId=0` 而非 NULL 表示根 → 无法建真正的自引用外键（0 不是合法 id） | 🟡 已知代价，可接受 |
| B7-2 | **无深度约束**：应用层若允许把二级分类设为父级，会产生三级甚至**环**（A.parent=B, B.parent=A） | 🟠 缺陷 |
| B7-3 | 删除分类 CASCADE 掉全部交易（**含回收站中的**） | 🔴 见 B5-6 / B1-4 |
| B7-4 | 系统分类无删除保护（数据层） | 🔴 见 B1-4 |
| B7-5 | 父分类被删，子分类的 `parentId` 悬空（指向不存在的 id）→ 子分类既非一级（`parentId≠0`）也无父 → **在树形 UI 中"消失"** | 🟠 缺陷 |

### 7.3 攻克方案

| 缺陷 | 方案 | 验收标准 |
|---|---|---|
| B7-2 | UseCase 层校验：`require(parent.isMajor)`（父必须是一级）+ `require(parentId != self.id)` | 单测：设二级分类为父 → 抛异常；自引用 → 抛异常 |
| B7-3/B7-4 | 见难点 1 §1.5 与难点 5 §5.5 | — |
| B7-5 | 删除父分类时，子分类 `parentId` 置 0（升为一级）而非留悬空；或阻断删除并提示「请先处理 N 个子分类」 | 单测：删父分类 → 子分类 `parentId == 0` 且在列表中可见 |

### A.2 治理主线建议

三条主线，**顺序不可颠倒**：

```
【主线一 · 止血：防数据永久丢失】P0
  B1-4 系统分类删除保护
  B5-6 分类删除影响面提示（含回收站）
  B7-5 子分类升级为一级
  → 共同点：都是「一次误操作 = 不可恢复」，且改动量都很小，性价比最高

【主线二 · 加固：数据契约与精度】P1
  前置：迁移测试 + schemas 入库（见 02 文档 R2）—— 这是所有动数据操作的安全网
  ├─ B3-4 + D4-1 整数分全链路（一次迁移 + 一批 sumOf 改写）
  ├─ D4-2 + D4-3 预算唯一索引与外键（同一次 v7→v8 迁移完成）
  ├─ D2-1 + D2-2 周期算法统一 + 事务边界修正
  └─ P6-2 + P6-3 序列化收敛 + 历史备份样本库

【主线三 · 安全：备份加密】P0（可与主线一并行）
  P6-1 立即上风险文案 → 落地 PBKDF2+AES-GCM
  → 独立于其他主线，无依赖，可并行
```

**为什么主线二必须先做迁移测试**：D4-1/D4-2 都要动 `budgets` 表结构，且 D4-2 涉及「先去重再建唯一索引」这种一步错就让升级用户**启动即崩**的操作。没有 `MigrationTestHelper` 保护就动手，等于蒙眼手术。

**为什么主线一可以立刻做**：三个缺陷的修复全是**应用层校验与提示**，不动 schema、不动数据，风险极低，但挡住的是"用户数据永久丢失"这类不可逆事故。**先把不可逆的堵上，再做可逆的优化。**
