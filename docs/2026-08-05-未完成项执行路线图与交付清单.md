## 〇、铁律（动手前先刻进脑子）

| # | 铁律 | 违反代价 |
|---|---|---|
| CT-1 | **APK 只能由 GitHub Actions CI 构建，禁止本地构建**；编译验证以 CI 为准 | 本地"通过"= 没通过；一次翻车 = 一轮 CI 空转 |

| CT-5 | 重发同版本必须先 `DELETE /releases/{id}` | 否则 release 守卫跳过创建，新 APK 挂不上 |
| V-1 | 迁移 SQL 的外键/索引/列**逐字对齐** Room 导出 `N.json`（SQLite 省略 `ON DELETE` 默认等同，但 Room 校验逐字符比，缺即崩——见 v1.6.31 血案） | 升级用户启动即闪退 |
| V-2 | `N.json` 必须在同一 PR 提交入库，`(N-1)→N` 的 MigrationTest **禁止 @Ignore** | @Ignore 等待期 = 无防护网 = 重演 v1.6.31 |

## 二、执行路线图（限时作战图）

> 排期原则（沿用 `04`）：**不可逆 > 可逆**；动 schema 前必须安全网就位；每批次独立 CI，禁止合并一把梭。
> 单人维护，按每 Sprint 8 人日容量估算。本路线图不按 2 周固定 Sprint，按**任务依赖 + 风险**串成 6 个交付波次。

```
Wave A（安全网补强 · 1 周）  ── T-3 历史迁移测试 + T-5 报告补录
   │  理由：U-12 动 accounts/recurring/template schema 前，必须有迁移测试兜底
   ▼
Wave B（加密 UX 闭环 · 0.5 周）── T-1 口令 UI 入口 + T-2 提示文案
   │  理由：代码能力已就绪，仅差用户交互；零 schema 风险，顺手收口
   ▼
Wave C（P3 清理 · 0.5 周）────── T-4 P3-1 余额 SQL 聚合 + P3-2 依赖清理
   │  理由：纯性能/清理，零 schema 风险，可与 B 并行
   ▼
Wave D（测试模块独立化 · 1 周）── U-8 testing/ 子项目 + 迁移现有 test
   │  理由：M4 重构的安全网；先有独立测试模块，重构才有落脚处
   ▼
Wave E（M4 分层重构 · 2 周）──── U-9 di/ + utils→core + domain 层 + U-11 周期抽层
   │  理由：依赖 Wave D 测试网；每批次独立 CI + release 真机回归（CT-3）
   ▼
Wave F（M4 文件收敛 · 1.5 周）─ U-10 拆巨型文件 + navigation 抽出 + Lint 400 行升 error
   │  理由：依赖 Wave E 包结构就位
   ▼
Wave G（PHASE4 金额迁移 · 1.5 周）─ U-12 accounts/recurring/template 迁 Long 分 + 迁移测试 + （上架时）包名迁移
      理由：最高风险 schema 变更，必须最后做、严格走真机升级回归门禁（V-1/V-2）
```

**关键路径长度 ≈ 8 周**（A→D→E→F→G，B/C 可并行插入）。
