## 二、目标目录结构与模块划分决策

### 2.1 决策：**保持单模块，内部分包收敛**（不拆多模块）

| 维度 | 拆多模块（`:core:data` / `:core:ui` / `:feature:*`） | 单模块内部分包收敛 ✅ |
|---|---|---|
| 编译提速 | 10112 行总量，全量编译本就不慢，收益 <10% | 无损失 |
| 强制解耦 | 编译期强约束，效果最好 | 靠约定 + Review + Lint |
| 迁移成本 | 需重排 75 文件 + 8 份 gradle + KSP/Room schema 路径迁移 | 仅移动文件与改 package |
| 风险 | **高**——项目硬性约束"APK 只能由 CI 构建"，多模块化一次翻车就是一轮 CI 空转 | 低，可分批 |
| 团队规模 | 多模块的价值在于多人并行；本项目单人维护 | 匹配 |

**结论：拒绝多模块。** 理由用一句话讲透：多模块解决的是「编译慢 + 多人抢改同一文件」，这两个痛点在 10112 行单人项目上都不成立，而它引入的成本（S5 尚未解决就先动 8 份 gradle）会直接放大 CI-only 构建约束下的返工代价。

> 预留升级触发条件（满足任意两条再启动多模块化）：代码量 >30000 行；协作者 ≥3；全量构建 >5 分钟；出现需要独立发布的 SDK/Wear/TV 变体。

### 2.3 拆分批次（低风险演进路径）

| 批次 | 内容 | 触碰文件 | 验收 |
|---|---|---|---|
| B1 | 拆 `di/`，删除 `TransactionViewModelFactory.kt` | 3 | CI 编译通过 + 冷启动无 Koin 报错 |
| B2 | `utils/` → `core/*` 迁移 + ProGuard 同步 | 14 + 1 | **release 变体**构建通过 + 备份导出导入回归 |
| B3 | 建 `domain/`，迁 Statistics/Recurring，抽账户余额 UseCase | 5 | 既有 4 个单测继续绿 + 新增 UseCase 测试 |
| B4 | `data/local` 分层 | 28 | Room KSP 通过 + `schemas/` 无 diff |
| B5 | `feature/` 收敛 + 拆巨型文件 | 19 | 每文件 ≤400 行 |
| B6 | `navigation/` 抽出 | 1 | 全路由手工走查 |

**批次间必须各自跑一次 CI**，禁止合并批次一把梭——本项目禁止本地构建，一次合并翻车的定位成本是多轮 CI。

## 三、命名规范

### 3.1 包与文件

| 对象 | 规则 | 正例 | 反例 |
|---|---|---|---|
| 包名 | 全小写，单数名词，不用下划线 | `domain.usecase.budget` | `domain.useCases`、`domain.budget_uc` |
| 类文件 | 一文件一主类，文件名 = 类名 | `BudgetRepository.kt` | `Repos.kt` |
| Composable 文件 | 页面 `XxxScreen.kt`；片段 `XxxSection.kt`；对话框 `XxxDialog.kt` | `StatisticsTrendSection.kt` | `SettingsSections.kt`（复数、承载多个不相关组件） |
| 单文件上限 | **400 行**，超出必须拆 | — | 现存 8 个违规文件 |

### 3.2 代码符号

| 对象 | 规则 | 示例 |
|---|---|---|
| Composable | 大驼峰，名词短语，无副作用后缀 | `TransactionItemCard()` |
| ViewModel | `<领域>ViewModel` | `BudgetViewModel` |
| UiState | `<领域>UiState`，`data class`，字段全部有默认值 | `data class HomeUiState(val loading: Boolean = false, ...)` |
| 事件 | `on<动词><宾语>` | `onDeleteTransaction` |
| UseCase | `<动词><宾语>UseCase`，暴露单一 `operator fun invoke` | `CalculateAccountBalanceUseCase` |
| DAO 方法 | 查询 `get*`（挂起单次）/ `observe*`（Flow）/ `*Snapshot`（一次性 List）；写 `insert/update/delete/purge/restore` | 现有 `observeAll()` / `getAllSnapshot()` ✅ 符合 |
| Repository 方法 | **必须显式包装 DAO**，禁止直接暴露 DAO 实例 | 历史踩坑：缺 `BudgetRepository.insert` / `TagRepository.deleteAll` 导致 `Unresolved reference` |

### 3.3 数据库列名（现存不一致，必须冻结规则）

实测现状：`amount_cents` / `deleted_at` 为蛇形，`categoryId` / `accountId` / `sortOrder` / `isDefault` / `nextRunDate` 为驼峰——**同一张 `transactions` 表内两种风格并存**。

**规则：存量列名一律冻结，不做重命名。** 理由：列重命名在 SQLite 需走「建新表 → 拷数据 → 删旧表 → 改名」四步（`MIGRATION_6_7` 已为 `amount` → `amount_cents` 付过一次这个代价），纯风格收益不值这个迁移风险与备份 DTO 兼容代价。

**新增列一律使用 snake_case + 显式 `@ColumnInfo(name=...)`**，与 `amount_cents`/`deleted_at` 保持一致，逐步单向收敛。

### 3.4 资源与测试

| 对象 | 规则 |
|---|---|
| 资源 | `<类型>_<模块>_<语义>`，如 `ic_tab_home.xml`、`bg_widget_card.xml` |
| 字符串 | `<模块>_<语义>`，如 `settings_backup_title` |
| 单元测试 | `<被测类>Test.kt`；方法名 `<场景>_<条件>_<预期>`，如 `computeNextRun_monthlyOn31st_clampsToMonthEnd` |
| 迁移测试 | `Migration<N>To<N+1>Test.kt` |

### 3.5 Git

| 对象 | 规则 |
|---|---|
| 分支 | `feat/<域>-<简述>`、`fix/<域>-<简述>`、`chore/<简述>`、`refactor/<批次号>-<简述>`（如 `refactor/b2-utils-to-core`） |
| Commit | Conventional Commits：`feat(budget): ...` / `fix(backup): ...` / `refactor(di): ...` |
| Tag | `v<major>.<minor>.<patch>`，**必须是 annotated tag**（lightweight tag 不触发 release 产物挂载） |
| 版本号 | `versionName` 与 tag 严格一致；`versionCode` 单调递增，每次发版 +1 |

### 4.1 Gson 与 kotlinx-serialization 并存问题及收敛方向

**现状**：两套序列化框架同时存在。Gson 承载备份/恢复（DTO 位于 `utils` 包，靠**字段名反射 + 泛型签名**工作），kotlinx-serialization 承载其余场景。

**风险**：这是 release 包历史崩溃的根因——R8 裁剪泛型签名后，`List<TransactionImport>` 的元素类型在运行时绑定到错误类，抛 `p6.n cannot be cast to z5.h`。ProGuard 里那两条 `-keep ... { *; }` 是**为 Gson 的反射机制打的补丁**，代价是这两个包完全放弃混淆与裁剪。

**收敛方向（三步，不可跳步）**：

1. **冻结**：任何新增序列化需求一律 kotlinx-serialization，Gson 只读存量。
2. **双写过渡**：备份 DTO 增加 `@Serializable` 注解；导出改用 kotlinx 写，导入保持"先试 kotlinx，失败回退 Gson"，覆盖老版本备份文件。
3. **摘除**：确认线上无 Gson 格式备份需恢复后，移除 Gson 依赖，同步删掉两条 `-keep { *; }`，恢复 R8 对这两个包的裁剪。

**验收标准**：每一步都必须以 **release 变体 CI 构建 + 真机"导出→卸载重装→导入"回归**为准。debug 包不混淆，**测不出这类问题**。

## 五、基础架构骨架

### 5.1 DI 分层（拆解 42 行单文件 `KoinModule.kt`）

```kotlin
// di/DatabaseModule.kt
val databaseModule = module {
    single { JianjiDatabase.getDatabase(androidContext()) }
    single { get<JianjiDatabase>().transactionDao() }
    // ... 其余 7 个 DAO
}

// di/RepositoryModule.kt —— 绑定到 domain 接口，而非具体类
val repositoryModule = module {
    single<TransactionRepositoryContract> { TransactionRepository(get()) }
    // ...
}

// di/DomainModule.kt
val domainModule = module {
    factory { CalculateAccountBalanceUseCase(get()) }
    factory { CalculateBudgetUsageUseCase(get(), get()) }
    factory { ComputeRecurringNextRunUseCase() }
}

// di/ViewModelModule.kt
val viewModelModule = module {
    viewModel { TransactionViewModel(androidApplication(), get(), get(), get(), get(), get()) }
    // ...
}

// JianjiApplication.kt
startKoin {
    androidContext(this@JianjiApplication)
    modules(databaseModule, repositoryModule, domainModule, viewModelModule)
}
```

**约束**：
- `single` 只给无状态、进程级唯一的对象（DB / DAO / Repository）
- `factory` 给 UseCase（无状态，随用随建）
- `viewModel` 只在 `viewModelModule`
- ❌ 禁止在模块外使用 `GlobalContext.get()` 做服务定位

**验收**：`TransactionViewModelFactory.kt` 从仓库中消失；全局搜索 `ViewModelProvider.Factory` 结果为 0。

### 5.2 错误处理与日志

```kotlin
// ❌ 禁止
try { risky() } catch (e: Exception) { }

// ✅ 要求
try {
    risky()
} catch (e: IOException) {
    Timber.e(e, "backup: write failed, path=%s", path)
    _uiState.update { it.copy(error = UiError.BackupWriteFailed) }
}
```

| 规则 | 内容 |
|---|---|
| 日志出口 | 仅 Timber。`Timber.plant()` 只在 debug 变体种 `DebugTree` |
| 禁止 | 静默 catch、吞掉 `CancellationException`、日志里打印金额明文之外的敏感信息（备份密码/密钥绝不入日志） |
| 用户可见错误 | 必须经 `UiState.error` 呈现，禁止只写日志不给反馈（历史教训：`BudgetSettingsDialog` 在 `budgetVM == null` 时**静默失败**，用户看到"设置了但恒为 0"，见 `BUGFIX_ROADMAP_budget_account.md` §七.2） |
| 可选依赖为 null | 一律给可见反馈或直接 `require` 崩在开发期，禁止静默降级 |

### 5.3 协程与 Dispatcher

| 场景 | 约定 |
|---|---|
| ViewModel | `viewModelScope`，禁止 `GlobalScope` |
| DB 读写 | 依赖 Room 内建线程池，DAO `suspend`/`Flow` **不再额外套 `withContext(IO)`** |
| 文件 IO（备份/导出/海报） | 显式 `withContext(Dispatchers.IO)` |
| CPU 密集（统计聚合） | `withContext(Dispatchers.Default)` |
| Dispatcher 注入 | UseCase 构造参数接收 `CoroutineDispatcher`，默认值给生产实现，测试传 `UnconfinedTestDispatcher` |

### 5.4 Flow / UiState

```kotlin
data class HomeUiState(
    val isLoading: Boolean = true,
    val monthIncome: Long = 0L,       // 分
    val monthExpense: Long = 0L,
    val transactions: List<Transaction> = emptyList(),
    val error: UiError? = null
)
```

| 规则 | 内容 | 依据 |
|---|---|---|
| 单一状态源 | 一个 Screen 一个 `StateFlow<XxxUiState>`，禁止多个平行 `StateFlow` 拼装 UI | — |
| `stateIn` 策略 | **默认 `SharingStarted.Eagerly`**；使用 `WhileSubscribed` 必须在注释中说明为何安全 | 历史 bug：`WhileSubscribed(5000)` 导致账户余额恒显示 ¥0.00，修复即改 `Eagerly`（`TransactionViewModel.kt:87`） |
| 跨 Screen 共享 VM | 必须在 NavHost 层显式传参，禁止靠"某处已创建"的隐式假设 | 历史 bug：`JianjiApp.kt:264` 漏传 `budgetVM=` 导致预算恒为 0 |
| 金额单位 | UiState 内部一律 `Long`（分），**仅在渲染的最后一刻**除 100 | `amount_cents` 设计意图 |

### 5.5 数据库迁移与 schema 基线

| 规则 | 内容 |
|---|---|
| version 变更 | 每次改 Entity 必须 `version++` **且**写 `Migration`，并在 `addMigrations(...)` 注册 |
| schema 基线 | `app/schemas/*.json` **必须提交入库**（当前尚未入库，见 S5），它是 `MigrationTestHelper` 的唯一基线。2026-08-04 注：v7→v8 已用不依赖 schemas 的 `Migration7to8Test` 冒烟测试在 CI 通过，但 schemas 入库仍建议补齐 |
| 迁移测试 | 每条 `MIGRATION_N_N+1` 配一个 `MigrationNToN+1Test`，验证：表结构、**数据不丢**、索引存在 |
| `fallbackToDestructiveMigration` | 当前已开启，用途**仅限降级容灾**（避免回退旧版闪退）。❌ 禁止用它替代升级路径的 Migration |
| 现有迁移资产 | v1→v7 共 6 条；`MIGRATION_6_7` 完成 `amount REAL → amount_cents INTEGER`（三张表）+ 移除 `accounts.balance`；`MIGRATION_4_5` 建 `date` 索引 |
| 索引变更 | Entity 的 `indices` 与 Migration 的 `CREATE INDEX` **必须成对出现**，否则新装用户与升级用户索引不一致 |

### 5.6 ProGuard 约定

| 规则 | 内容 |
|---|---|
| 新增反射/序列化 DTO | 必须同步加 `-keep`，并在规则旁注释「为什么」 |
| 禁止 | 为图省事 `-keep class com.example.jianji.** { *; }`（等于关闭 R8，包体膨胀） |
| 强制验证 | 任何影响 `data`/`core.io`/DTO 包结构的改动，**必须构建 release 变体并真机跑一次备份导出→导入** |
| 排错口诀 | release-only 崩溃 + Gson + 类名被混淆（如 `p6.n`）→ 查 keep 是否覆盖全部反射 DTO 包 |

### 5.7 构建与 CI 约束（硬性）

| 规则 | 内容 |
|---|---|
| 构建方式 | **APK 必须由 GitHub Actions 构建，禁止本地构建**。本地 lint 为 0 ≠ 能编译 |
| 编译验证 | 一律以 CI 结果为准 |
| 触发 | `push main` / `tag v*` / PR / `workflow_dispatch`；tag push 触发 release 产物 |
| 重发同版本 | 必须先 `DELETE /releases/{id}`，否则 workflow 的 `Check if release already exists` 守卫会跳过创建，新 APK 挂不上 |
| 排错 | 抓 Job 日志中的 `e: file:///` 行，而非只看 `BUILD FAILED` |
| 签名 | CI 用 `KEYSTORE_FILE` 等 4 个环境变量；本地 debug 回退 debug 签名 |
